**A 4B Qwen model, post-trained with SFT and Postgres-in-the-loop RL, cut mean latency 44.7% across 113 join-heavy queries by emitting hint-annotated SQL that steers join order and access paths.** The setup runs multiple rollouts per query, executes each candidate plan on Postgres, and feeds back scalar rewards versus the default plan to nudge weights toward faster strategies. A custom GRPO variant stabilizes training in a noisy environment, backed by a measurement rig designed to reduce Linux page cache contention across concurrent containers. The model initially failed to produce valid plans for 99 queries, then learned to do so and outperform defaults, with examples showing wins like 74 ms vs 118 ms for the same query via different join hints.

Under the hood: Qwen generates hints such as HashJoin, Leading, NestLoop, and IndexScan; RL was split across machines (vLLM + trainer on a rented 2x H100 node; four Postgres containers locally), and off-policy distillation leveraged about 500 agent trajectories. The result frames join ordering as a control problem with a single, verifiable reward signal—execution time—using Postgres itself as the judge. The catch is measurement noise and scope: results are on a join-heavy suite with careful isolation, so portability to broader workloads remains to be proven.

### Reverse-engineered Jev-like model

**It scores a variable-length menu of text options against a context in one forward pass**, using per-option queries that attend over the context, a shared dot product for scores, and a softmax across options. Jev is TypeSafe’s commercial model for this task and its design isn’t public; this is an independent starter with the same input/output shape, not the original.

- **Architecture**: options → query vectors → attention over context tokens → one context vector per option → shared dot product → softmax over options.
- **Encoders**: default is a small byte-level encoder trained from scratch; optional path uses a frozen Hugging Face encoder with a learned scorer head. Checkpoints store only the head and the encoder name (not the encoder’s weights), so loading requires the same HF model.
- **Data & CLI**: JSONL with {context, options[], label} (variable N, min 2). Commands to synthesize data, train, evaluate, and predict are included. Evaluation reports top‑1/top‑3 accuracy and expected calibration error, plus a shuffled-context control baseline.
- **Limits & runtime**: default truncation is 192 bytes for context and 32 bytes for each option; adjustable via flags. Trains on CPU, Apple MPS, or CUDA.
- **Examples**: the same option-attention head is reused for vision control (Doom and chess) via jevlike.vision, with single‑game and shared 12‑option checkpoints and trace/film tooling. Demos are illustrative rather than competence claims.

Good fit if you want a transparent, small model for “choose one of N” menus with calibration; treat it as a starting point rather than a drop‑in replacement for Jev’s internals or performance.

- **Fast clones vs. accuracy:** Commenters evaluated other rapid attempts to replicate Jev's functionality, focusing heavily on a 1B-parameter Qwen-2.5 variant claiming 5x faster inference. ### Breaking the 1.58-bit Barrier for Ternary LLMs

#### [Submission URL](https://arxiv.org/abs/2609.16338) | 234 points | by [matt_d](https://news.ycombinator.com/user?id=matt_d) | [37 comments](https://news.ycombinator.com/item?id=49732931)

**Zero weights account for up to 51.5% in measured ternary LLMs, enabling a bitmap+sign layout (BITCOS) that packs down to 1.485 bits/weight—under the 1.585-bit figure and below the 1.625-bit five‑trit packing used in practice.** The trick is distribution-aware storage: a dense presence bitmap plus a compacted sign vector costs 2 − z bits/weight for zero density z, so it out-compresses five‑trit whenever z > 0.375 (which held for 26 of 29 models). The authors provide efficient unpackers for AVX2, AVX‑512, and Intel Xe2 GPUs, and benchmark against production ternary matvec kernels, realizing up to 1.28× speedup at real model sparsities. End-to-end LLM decode throughput improves by up to 1.18× on CPUs and 1.27× on GPUs across five platforms. The catch is baked into the formula: benefits scale with zero density; in the three models below ~37.5% zeros, five‑trit remained denser and the runtime gains shrink accordingly.

The thread centers on whether extreme sub-2-bit quantization is a practical architectural shift or an inherent "category error" that destroys model intelligence. Skeptics pointed out that storage size does not equal preserved information; in block-wise formats, outlier weights consume the limited dynamic range and starve the smaller weights, leading to degraded reasoning and looping at longer contexts despite passing standard benchmarks. Proponents countered that Quantization-Aware Training (QAT)—where the optimizer updates high-precision latent weights while only the forward pass is quantized—and scaling up raw model size can effectively offset the precision drop.

A secondary debate weighed ternary models against vector quantization. Critics argued that Post-Training Quantization (PTQ) paired with efficient GEMM kernels like FLUTE is a superior approach. Defenders emphasized that ternary's real breakthrough is compute-driven: reducing matrix multiplication to simple add/subtract operations directly relieves the memory bandwidth bottleneck between storage and compute that throttles standard inference. 

Regarding the BITCOS layout itself, commenters questioned why the authors stopped at a presence bitmap rather than using arithmetic coding or an 8-bit lookup table for 6-component vectors. The technical consensus was that fast random access requires decoding in small, 128-entry blocks, and because the ternary weights are roughly independent and identically distributed in practice, aggressive lookup table pruning would be ineffective.
