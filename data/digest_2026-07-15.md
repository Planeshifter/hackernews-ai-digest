### High-Bandwidth Flash offers efficient storage for model weights

#### [Submission URL](https://spectrum.ieee.org/high-bandwidth-flash) | 68 points | by [Gaishan](https://news.ycombinator.com/user?id=Gaishan) | [24 comments](https://news.ycombinator.com/item?id=48915393)

**Flash can deliver up to ~4.8 GB/s per die on reads**, and High Bandwidth Flash (HBF) borrows HBM’s playbook—3D packaging and vertical die stacking—to multiply that throughput from familiar NAND for serving model weights. NAND is dense and non-volatile but slow to write; leveraging fast reads matches weight-serving workloads, where bandwidth beats write speed. HBF still won’t rival DRAM/HBM—DDR5 reaches ~70.4 GB/s per DIMM and HBM4E ~3.6 TB/s per stack (about a 750x edge over flash)—but it offers a way to expand memory-side bandwidth without DRAM’s refresh power tax. With HBM/DRAM capacity tight and new fabs not slated to start production until 2027, SK Hynix and others frame HBF as a packaging-driven path to “vastly higher” flash bandwidth specifically tuned for read-heavy AI models.

The conversation centered on how perfectly NAND's native asymmetry—slow writes but massive, highly parallel reads—matches AI inference workloads. Commenters noted that shifting static model weights to Flash frees up expensive RAM for dynamic operations like KV caching.

The sharpest disagreement focused on the economics of advanced packaging. One critic argued that since HBM's exorbitant cost comes largely from packaging complexity and yield issues rather than the underlying DRAM, applying 3D stacking to cheap Flash won't guarantee a cheap product. In this view, swapping DRAM for Flash just ruins the bandwidth-to-capacity ratio (and thus tokens per second), yielding a niche product with worse price-to-performance. A counterargument noted that if HBF can deliver 1.6TB/s from a 512GB stack, it would drastically lower overall system costs compared to HBM, even if the user leaves most of the capacity empty. 

Elsewhere, the thread turned into a post-mortem for Intel's Optane, lamenting its discontinuation right before the AI memory crunch. However, commenters debated its applicability: Optane's core strength was ultra-low latency, whereas deep AI compute pipelines are largely latency-insensitive and bottlenecked almost entirely by pure bandwidth.

- Prefer the REST/JSON API over SSH, which becomes “death by a thousand cuts” for LLMs.
- Disable insecure services (insecure API port, www, telnet, ftp).
- Dump the full config before and after changes; put it under source control. Write a recovery runbook and rehearse it; an untested backup is junk.
- CAPsMAN makes multi-AP Wi‑Fi setups straightforward; LLMs handle its config well.
- Cross-check plans by asking multiple models (e.g., antigravity, codex, opus, fable) to converge on a consensus.
- Before a cutover, record SSIDs, passwords, and DHCP reservations.
- Break work into minimal steps and test after each change; LLMs hallucinate.
- Set NTP on every device, and give routers/switches/APs descriptive names; label switch ports to match reality.
- Keep devices on the same RouterOS version; have the LLM verify command syntax since it changes over time.
- When IPs conflict or you can’t reach the box by IP, use L2 “MAC Telnet” (mactelnet) so the LLM can still talk to the device; WinBox is GUI-only for humans (though now cross‑platform, including Mac).
- Physical Ethernet during changes is assumed; you don’t need an MCP server.
The throughline: treat the LLM like a fast but fallible junior — constrain the interface, keep diffs, and always keep an L2 escape hatch.

- **Operational caveats:** Practitioners warned that prompts must explicitly state whether a device runs RouterOS v6 or v7 to avoid syntax hallucinations.
