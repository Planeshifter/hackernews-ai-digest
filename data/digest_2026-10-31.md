### Show HN: A language model that lives in a boot sector

#### [Submission URL](https://github.com/kerlenton/bootgpt) | 92 points | by [kerlenton](https://news.ycombinator.com/user?id=kerlenton) | [6 comments](https://news.ycombinator.com/item?id=50315782)

**The entire inference engine fits in a 510-byte MBR**, and what it does with that space is hallucinate an endless Linux boot log: timestamps, PCI BARs, ACPI events for hardware that doesn't exist. The model is a char-level net with 8 characters of context and one hidden layer, int8 throughout, running in 16-bit real mode on a 386 with no OS and no C runtime.

The trick for fitting is moving everything that isn't code out of the sector. The 11.5 KB of weights, the vocab table, and the strings sit in the next 23 sectors, loaded via `int 13h`. The forward pass is `imul` plus a single `idiv` for a softclip activation, with power-of-two quantization scales so no floating point is needed. Sampling is argmax with timer-seeded noise, and any keypress reboots.

The best part is the debugging story. `train.py` replicates the asm's integer math exactly, LCG sampler included, so its output can be diffed char for char against QEMU. When the outputs diverged after the first few characters, the author dumped hidden-layer values over QEMU's debug port and found only neuron 0 was correct. The cause: `idiv` writes its remainder to `edx`, which was holding the bias table pointer. The fix derives the bias address from the loop counter. A second bug: the BIOS print routine clobbers `bx`, which held the predicted character, hence the push/pop around it.

Output quality is what you'd expect from that budget. Lines look like real dmesg until the values degrade into noise (`ryndrde c4128 6422 Vveine`). The 3 MB training corpus is synthetic, with one kernel version and disk per boot session, because real logs repeat themselves and that repetition is what makes a tiny model look sane.

It's the opposite tradeoff from sectorllm, which runs a real 5-layer llama2 with attention in about 1.2 KB of asm. bootgpt keeps the engine inside one sector and narrows the model to one job. The image is MIT-licensed and a normal boot image, so you can `dd` it to a USB stick and boot a BIOS machine; it only reads its own sectors.

The thread is almost entirely appreciation for the project as a piece of play, with no technical debate about the model, the assembly, or the bootloader.

- **Silly engineering as a virtue:** The top comment calls it "silly engineering that makes me appreciate humans" and says making silly things can be the goal, with no need for economic value or practicality. The author (kerlenton) agrees that most people drawn to software engineering feel that urge now and then. Another commenter compares it to the early web and an older YouTube, where people just shared cool things with each other.
- **How to learn this:** Asked how they learned to do this, the author gave no curriculum. ### AI text watermarking and quality loss

#### [Submission URL](https://blog.keyvan.net/p/ai-text-watermarking-and-quality) | 65 points | by [danielfoster](https://news.ycombinator.com/user?id=danielfoster) | [15 comments](https://news.ycombinator.com/item?id=50320599)

**Anthropic's "no quality impact" claim for Claude watermarking holds for a single response, and the SynthID-Text paper it rests on concedes as much.** Keyvan's argument is that the supplementary PDF admits a "diversity/detectability trade-off": watermarked responses to the same prompt are more similar to each other than unwatermarked ones. That doesn't square with the "just swapping random numbers" defense popular in the Gruber debate.

The paper itself says this "could lower the overall quality of a system which generates many responses then selects the best one." Keyvan's point is that the same applies to ordinary use. Hit retry on a sentence rewrite and you get the loaded-die effect, with near-duplicate answers where an unwatermarked model would vary.

Evidence is thin but concrete. Consultant Natzir Turrado reproduced SynthID-Text on an open model with the paper's settings and asked for a memorable coastal-town trip five times. **Four of five watermarked answers opened almost identically** ("My heart still sings/dances when I think back…"), versus three distinct openings without the watermark. That's one small test, not a benchmark.

Keyvan also raises two untested extensions:
- Because the watermark keys off a short sliding context window, identical short phrases across different prompts could recreate the same context and push output toward the same continuations.
- Consensus-based confidence checks, which repeat a prompt and look for agreement to flag hallucinations, would be skewed by artificially correlated samples.

The author sides with Gruber, though only on the narrower claim that quality loss across repeated use is real, not that watermarking wrecks any single answer. The source text cuts off before his full conclusion.

The thread turns on one question: is diversity loss a quality loss? The author (k1m) says yes in many applications, and the critics say no.

**The "it's a different thing" camp (viraptor, Majromax):** Majromax gave the most technical rebuttal. SynthID-style watermarking changes only the random seed, which becomes context-sensitive by keying on the prior N tokens plus a secret key. Averaged over seeds, the next-token distribution is unchanged, so one-shot quality can't change. What does change is sample diversity. Using SynthID is like fixing the PRNG seed, so repeated generations of the same prompt converge. Majromax called "diversity" and "quality" distinct concepts and said conflating them leads to poor intuition. The real casualty is anyone sampling repeatedly to infer a probability distribution, such as calibrated-answer or consensus classifiers.

viraptor made a parallel point. The paper says non-distortionary watermarking leaves response quality intact but may change *system* quality, and the article drops the word "system." Less diversity could even mean more consistent output, and people who want a deterministic temperature=0 would welcome it. They also called the re-roll example weak, since you can iterate in-thread or ask for 20 alternatives. Their bottom line was "show us the actual benchmarks."

**The author's reply (k1m):** Quality is defined by the application, and even the paper's authors say watermarking can lower a system's quality. Re-roll buttons are a familiar feature, and asking for N alternatives in one thread isn't equivalent, because earlier answers anchor later ones. Viraptor countered that being steered away from the previous answer is the point, and asked for a definition of "too much."

**The evidence dispute:** ethanj8011 called the 4/5 vs. 2/5 coastal-town test obviously invalid. dannyw pointed to the linked Spanish article, which reportedly ran 30 prompts at 5 pairs each, about 300 samples. ethanj8011 accepted that it lines up with the original findings, but thought more elaborate watermarking schemes could ameliorate the effect. They also doubt text watermarking works as a governance tool.

**Other reactions:**
- cowlby joked that Claude already watermarks everything with "You're half right, and the half that's wrong is the useful part." oidar and zdc1 riffed on spotting "Claudisms" as a de facto watermark.
- Benjaminsen said models are inherently poor at diverse output and plugged modelsalt.com as a fix.
- cleandreams welcomed watermarking, with output that is "serviceable but not exceptional."
- octoberfranklin accused proponents of gaslighting.

The unresolved crux is that no one produced benchmarks showing a downstream quality drop. The theoretical side agrees the single-sample distribution is unchanged, and the dispute is over whether correlated samples matter in practice.

### Do the math: How we took over ChatGPT accounts

#### [Submission URL](https://www.parameter.ai/labs/we-found-a-gap-at-openai) | 357 points | by [armcat](https://news.ycombinator.com/user?id=armcat) | [176 comments](https://news.ycombinator.com/item?id=50314699)

**A single shared ChatGPT link was enough to run attacker JavaScript as chatgpt.com in the victim's signed-in session**, per Parameter's research team. The payload could list conversations, pull a private chat that was never shared, exfiltrate it, and call authenticated APIs as the victim. OpenAI fixed it on October 26 and rated it P1.

The chain stitched together three individually harmless pieces:

- **Sandbox escape via postMessage.** The HTML Preview runs in a restricted cross-origin frame and can't read the parent page. But a shared conversation's interactive graph loads MathLive, which installs a listener in the main page for virtual-keyboard messages. That listener used an origin policy of "none" and didn't check the sender, so the Preview could send an `update-setting` message replacing the keyboard layout with arbitrary HTML.
- **HTML injection.** MathLive joined that layout into a string and assigned it to `innerHTML` in the real ChatGPT page. A `createHTML` helper looked like a sanitizer but just marked the string trusted. The injected `srcdoc` iframe had no sandbox attribute and inherited the chatgpt.com origin, giving it parent access.
- **CSP bypass via YouTube JSONP.** The CSP blocked inline script but allowed YouTube. YouTube's oEmbed endpoint reflected the `callback` parameter into the response even when it returned a validation error, so the response was valid attacker-chosen JavaScript served from an allowlisted domain.

The victim needed no install, paste, or dev tools; opening the link was the whole interaction.

The lesson is architectural: the cross-origin sandbox held, and the hole was a third-party library's message handler in the trusted page. Any allowlisted origin with a reflective JSONP endpoint also quietly undermines a CSP. The excerpt cuts off before the final exploit and the full disclosure timeline.

### Prospero: A new coding harness for a more civilized age

#### [Submission URL](https://nullprogram.com/blog/2026/10/31/) | 201 points | by [fovc](https://news.ycombinator.com/user?id=fovc) | [131 comments](https://news.ycombinator.com/item?id=50315226)

**Prospero is a C++ coding harness with a Dear ImGui docking GUI that Chris Wellons says uses about two orders of magnitude less memory than the web-stack harnesses.** His argument is that a harness is "essentially curl glued to popen()" and shouldn't need gigabytes of RAM.

It ships with no model providers built in. You bring your own endpoint: llama.cpp, an on-prem model, OpenRouter, or the Anthropic or OpenAI APIs. Claude subscriptions don't work. The harness supports subagents and agent-to-agent messaging. It can also deploy a headless copy of itself over SSH or WSL, so the engine runs on the target host while the GUI stays on your desktop. That split is why there's no TUI, and a session can keep running with the GUI detached and be re-attached later.

Standout features:
- **Desktop control:** a vision-capable model can see the screen and click, type, and drag to test GUI apps, with no per-app MCP server. The Professional Edition embeds engines for x86/x86-64 and ARM64 on macOS, Windows, and Linux. The Windows x86 engine runs on XP.
- **"Never wait forever":** every operation has a deadline. An unanswered permission request becomes a denial by timeout, network calls have timeouts, and watchdogs catch hangs. This is aimed at overnight runs that die on a trivial stall.
- **Passive rendering:** it redraws only when something changes, rather than on every vsync, so it doesn't use the GPU while an agent waits on a build.
