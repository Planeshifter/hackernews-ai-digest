### LLMs are making formal software verification feasible at a much larger scale

#### [Submission URL](https://www.anthropic.com/research/formal-verification) | 436 points | by [johnbender](https://news.ycombinator.com/user?id=johnbender) | [275 comments](https://news.ycombinator.com/item?id=50202217)

**Claude autonomously proved crash-freedom properties for 123 open-source libraries at the RISC-V assembly level**, in a collaboration with Theorem. Anthropic says this is the first large-scale AI-driven verification of production software at that layer. The motivation is defensive: if models can find and chain bugs faster than humans can patch them, testing alone stops being enough.

The proven property is narrow but real. Each program always exits normally, with no memory-safety errors or failing assertions, for every input under 64 MB and every modeled Linux OS response and memory layout. That holds only under stated assumptions: a single-threaded static binary, a fixed memory budget, RISC-V, and Linux. Anthropic itself calls this "still far away from fixing all possible bugs."

The main obstacle to verifying most software is the spec, since nobody can say formally what a "correct" text editor is. Anthropic's workaround is to automatically convert each library's existing tests into the specification, and the post is truncated right as it starts to explain how. The cost argument is the familiar one: seL4 took 2 person-years to build and 20 to verify. Claude's pitch is that proof effort falls as models improve and as proofs get reused across codebases.

Claude also found bugs that had survived years of testing, "despite trillions of test runs." The post doesn't name them in the visible text.

Released alongside:
- A subset of the proofs, plus the RISC-V and OS semantics, so anyone can check them.
- A Claude skill from Theorem for verifying your own code.
- An offer from Theorem to run the same pipeline on other open-source projects.

The post also previews smaller experiments: assessing zlib's security, and proving behavioral equivalence of a Python interpreter written in Rust.

The proofs are only as trustworthy as the models of RISC-V and the OS they rest on. That makes the published semantics the part worth scrutinizing.

Nearly the whole thread orbits one commenter's side project. malisper, who is rewriting Postgres in Rust, described a pipeline that compiles both C and Rust into Lean and has an LLM prove the two versions equivalent. About 12% of the code (roughly 70k lines of C) is proven so far, and the proofs have turned up only minor differences, such as floating-point results that vary across platforms. There is almost no discussion of the Anthropic/Theorem RISC-V work itself.

**Challenges to the approach**
- **The spec problem.** remywang objected that the spec here is just 2.6M lines of C, and that a human-readable spec would need something simpler than SQL, such as his own Prela language. dchftcs countered that for bug-for-bug compatibility the code is the best spec. - **Compiler trust.** remywang also asked who verifies the C/Rust-to-Lean compiler. malisper admitted he hasn't, and said the goal is bug-finding, not a trusted proof. naasking pointed to CompCert as precedent for formal C semantics.

### WorldTUI: I trained a 360M model to pretend to be a terminal

#### [Submission URL](https://simedw.com/2026/10/21/world-model-terminal/) | 599 points | by [alphax314](https://news.ycombinator.com/user?id=alphax314) | [181 comments](https://news.ycombinator.com/item?id=50190363)

**A 360M-parameter model, fine-tuned from Qwen2.5-Coder-0.5B, acts as a terminal with no shell or filesystem behind it.** Every keypress goes in as raw bytes, and the model predicts which screen rows change. It can create files, run vim and tmux, and play snake, and it usually remembers what you wrote a few commands later. The demo runs in-browser (208 MB, WebGPU, desktop Chrome or Edge recommended). Type `pythoon` to see that it's not a real shell.

The design choice that makes this work is treating the terminal as a grid rather than a text stream. The model sees a snapshot (size, contents, cursor), then emits row rewrites plus a cursor position per keypress. Two tricks keep this cheap:

- **COPY ops:** a scroll that would cost about 3,000 tokens as full row rewrites becomes three tokens per row, by referencing rows from the previous screen. The same op covers clear, vim line insert/delete, and man page navigation.
- **Tiny vocabulary:** 333 tokens (256 byte tokens reused for characters and coordinates, 64 row tokens, a few special ops), with grammar-constrained decoding so every output is a valid screen update. A WAIT token with a duration lets snake advance without input.

Training data is synthetic: real programs run in Docker with randomized personas, prompts, and terminal sizes, plus a 1.2% typo rate and 35% of sessions starting mid-task. The final set is 336k episodes, around 2B tokens, a rounding error next to the base model's roughly 18T. The author says the biggest wins were teaching the model to repair its own mistakes and decoding screen rows in parallel.

The real question was whether the model keeps a consistent world or just produces plausible output. "Usually remembers" is the honest answer, and it does better starting from bash than from mid-application states like vim or snake. The provided text cuts off before the training details and results, so how often it breaks down isn't quantified here.

### OpenShell – A safe, private runtime for fleets of autonomous AI agents

#### [Submission URL](https://github.com/NVIDIA/OpenShell) | 487 points | by [niemandhier](https://news.ycombinator.com/user?id=niemandhier) | [211 comments](https://news.ycombinator.com/item?id=50198675)

**Agents never see real credentials.** OpenShell, NVIDIA's open-source sandbox runtime, injects secrets only into requests headed for approved endpoints, so a compromised or confused agent has nothing to exfiltrate.

Enforcement is kernel-level. Each agent runs in an isolated sandbox where kernel controls limit file access and syscalls, and every outbound connection passes a policy check. You declare filesystem, network, and process rules per agent in a policy file.

The less common piece is the **formal verification of policy changes**. When an agent asks for more access, such as a new host reached with credentials or a new API method, OpenShell's prover flags the risky delta and holds it for human review. That makes the approval loop concrete: the agent works, hits a wall, and you approve a specific expansion rather than loosening everything up front.

- **Setup:** a curl-pipe installer sets up the CLI and a local gateway, then `openshell sandbox create --name demo`. The default image is bare Ubuntu with no agent installed. The walkthrough runs OpenCode against a free OpenRouter model.
- **Platforms:** Linux, macOS on Apple Silicon, and Windows via WSL 2 (experimental), with Docker, Podman, or host virtualization.
- **Scale:** a Helm chart deploys the gateway on Kubernetes, but your CNI must enforce NetworkPolicy.
- **Integration:** SDKs for Python, TypeScript, Go, and Rust, plus installable agent skills (`npx skills add NVIDIA/OpenShell`) that teach a coding agent to write policies and debug the gateway.

It's at 0.1.x, so expect API churn despite the stated stable release cadence. It also collects anonymous operational telemetry, which is on by default. Names, paths, prompts, and credentials are excluded, and `OPENSHELL_TELEMETRY_ENABLED=false` turns it off.

The thread splits between people sharing their own isolation setups and people pointing at the problem sandboxes still don't solve: data leaving through channels that are allowed.

**Collusion across agents.** The most substantive post, relayed from the GTC pitch, says per-agent permissions aren't enough. Agents in a fleet must communicate, so one can delegate a forbidden action to another that holds the right permissions. In the example, a collector, a report writer and a publisher can combine to publish raw data that no single agent could. OpenShell is said to track the fleet's collective permissions, and to be paired with Sentry, a BlueField-based hardware firewall that stops agents from editing their own policies. One reply joked about a loyal "double agent" overseer, then offered the practical version: a deterministic PII scrubber before and after processing, with an alert if PII ever appears downstream.

**Exfiltration through allowed channels.**
- fennecbutt uses iron proxy for domain restrictions and credential swapping, but worries about a prompt-injected agent leaking data a few characters at a time to an approved domain. They also proxy `gh` heavily to prevent forks, PRs and issues.
- igorhvr recommended matchlock, which uses Firecracker VMs and placeholder secrets swapped in at the network layer. They noted it doesn't solve exfiltration either.
- Proposed mitigations were network logging and a fingerprint check that scores outbound bytes against the protected dataset, pausing the agent when matches accumulate. LoganDark floated MITMing all TLS, but pinned certificates get in the way. A small anomaly-detection model was also suggested, and got the quip that it would need its own monitor.

**Skepticism about the pitch.** smallnix argued that the marketing blurb hides an oxymoron: more access means more capability, so a tool can only strike a balance, not deliver both at once. pradn took the opposite view, arguing that frontier models already escape sandboxes. They say the only durable answer is security by construction, with formally verified layers from chip to application.

**"Just use containers or VMs."** This branch was the longest.

- smokel pointed out that many people run NodeJS libraries bare, which is riskier.
- devmor countered that default Docker/containerd setups don't isolate much. They run agents on dedicated physical machines on their own VLAN, with scoped tokens and hardware-token-gated credentials.

- Bnjoroge and binsquare (the smolvm maintainer) pitched smolvm and microsandbox for faster boot (under 200ms) and built-in egress control and secrets handling. adastra22 and Twirrim noted that Lima is also just a hypervisor-backed VM, so the difference is mostly ergonomics.

### OpenAI CLI

#### [Submission URL](https://github.com/openai/openai-cli) | 240 points | by [armcat](https://news.ycombinator.com/user?id=armcat) | [111 comments](https://news.ycombinator.com/item?id=50191507)

**A first-party `openai` binary now wraps the whole REST API**, resource by resource, so you can generate images, upload files, run batches, and pull admin usage data from a shell script without writing client code. It's written in Go and ships prebuilt for macOS, Linux, and Windows. Install via GitHub Releases, `brew install openai/tools/openai`, or `go install` (Go 1.26+).

Commands mirror the API's structure (`openai <resource> [subresource...] <command>`). Scripting is the point, and the output handling shows it:

- `--format json|jsonl|yaml|raw` for machine-readable output (default is human text, even in pipes, so set the format explicitly when parsing)
- `--transform` takes GJSON paths to pull out fields without needing `jq`
- Errors go to stderr, with `--format-error json` for structured details
- `openai batches wait` blocks until a batch finishes and downloads results to a directory, which collapses a tedious poll-and-fetch loop into one command

Auth uses `OPENAI_API_KEY`, with a separate `OPENAI_ADMIN_KEY` for the admin endpoints such as organization usage.

The README is explicit that this is not Codex CLI: `openai` calls API operations, while `codex` is the coding agent.

One thing to check before rolling it into CI: self-managed release installs prepare **automatic updates** during eligible interactive runs. Set `OPENAI_CLI_NO_AUTO_UPDATE=1` to turn that off, or `OPENAI_CLI_NO_UPDATE_CHECK=1` to silence update checks entirely. Package-manager and Go installs only get notices. The repo shows signs of being generated from an API spec (a `generated` directory and a `.castiron` stats file), so expect command coverage to track the API closely.

### AI and the Enclosure of the Scientific Commons

#### [Submission URL](https://arxiv.org/abs/2610.27251) | 137 points | by [jrepinc](https://news.ycombinator.com/user?id=jrepinc) | [80 comments](https://news.ycombinator.com/item?id=50199230)

**The scientific literature is a commons, and the paper argues AI is the tool that finally makes enclosing it feasible**, in the same sense that England's common lands were enclosed and turned into private property between roughly 1600 and 1800.

P. K. G. Williams (an astrophysicist at the Harvard & Smithsonian Center for Astrophysics) starts from a correction to the usual framing. English agricultural commons didn't vanish through the "tragedy of the commons." They vanished through enclosure, which many observers then and now judge to have been theft at societal scale. Information commons are sturdier than pastures and, in his words, include some of humanity's greatest achievements. But he argues that doesn't make them immune, and that AI supplies the previously missing means of privatizing them.

The mechanism has two parts:
- **Extraction:** the commons gets converted into private wealth.
- **Erosion:** "slop spam" undermines the social systems that sustain the commons, such as the norms and institutions of scholarly communication.

He concedes AI enclosure doesn't work identically to the physical kind. The paper is a 14-page primer with 32 references, not an empirical study: it supplies the history and the economic and political frameworks, and offers them as a scholarly basis for the unease that AI is "not just a smash-and-grab, but an attack upon a whole way of life."

It's a framing essay, so expect argument by historical analogy rather than data. How well the analogy holds, given that scientific papers aren't depleted when copied, is the thing to test when you read it.

### Mini brain organoids ‘reading’ Braille key step towards biohybrid computing

#### [Submission URL](https://www.frontiersin.org/news/2026/10/16/mini-brain-organoids-reading-braille-biohybrid-computing-frontiers-artificial-intelligence) | 38 points | by [CharlesW](https://news.ycombinator.com/user?id=CharlesW) | [49 comments](https://news.ycombinator.com/item?id=50197450)

**Three brain organoids wired together decoded Braille letters 83% of the time; a single organoid managed 61%.** The Bristol team stimulated each organoid with electrical patterns derived from a tactile sensor scanning the 26 Braille letters, then trained a support vector machine on the organoids' neural responses to tell the letters apart.

The setup is modest. Each organoid is under a millimeter across and holds roughly 10,000 neurons. It sits on a multielectrode array that both delivers stimulation and records the response. The organoids act as a signal-transforming layer between sensor and classifier, not as a thinking substrate.

The more interesting result is noise robustness. When the researchers deliberately degraded the Braille signals with noise filters, the same SVM did worse decoding the raw obscured signals than decoding the organoid outputs. The authors don't explain why three organoids beat one. Their guess is that differences in network wiring, developmental state, and ongoing activity give each organoid complementary information. Liu concedes the flip side: if every organoid responds differently, a standardized, predictable system gets harder to build.

The limits are large:
- **No learning demonstrated.** The study shows signals being encoded, passed through, and decoded, not any long-term change in the organoids.
- **One task, fixed encoding.** It used a single tactile task, a fixed stimulation scheme, and a fairly simple measure of neural activity.
- **No energy numbers.** The efficiency case for biohybrid computing is the motivation, not something measured here.

Next steps are textures, edges, and other kinds of touch, then closed-loop tasks where the organoid gets feedback on its own output. That is the point where "relay" could become "learn." For now this is a feasibility check on the input-output channel, and 61% for a lone organoid is a long way from dependable hardware.
