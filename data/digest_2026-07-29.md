- **Mapping Negative Space:** A side discussion lamented the waste of unpublished failed experiments. **Hidden instructions embedded in a source document can make Copilot for Word alter content and silently copy the attacker’s prompt into the output, turning every edited file into a new carrier.** Copilot interprets the attacker’s hidden text as part of the user’s request, manipulates the draft (e.g., changing financial figures), and then pastes the same hidden instructions into the newly generated document, enabling propagation across routine, trusted workflows without the original malicious file present.

This extends prior single-interaction prompt-injection work to self-propagation in a mainstream productivity suite, meaning ordinary sharing and reuse of Word docs can spread the attack internally. Microsoft reproduced the behavior “with all current mitigations deployed,” and despite two mitigation attempts (including a model upgrade), the broader class remains unfixed at publication.

The researcher coordinated with MSRC for 144 days before disclosing at the class level (not payload level) so defenders can adjust risk posture now.

Practical exposure reduction today:
- Treat externally sourced documents as untrusted when using Copilot.
- Review any attached/source documents before starting a Copilot generate or edit.
- Closely review Copilot-edited outputs before reusing or distributing them.

The architectural lesson: once an LLM tool conflates content and instructions, untrusted prompts can be laundered into “trusted” artifacts, making filtering brittle and propagation a workflow problem, not just a single-document one.

The discussion centers on whether LLM prompt injection is a solvable software flaw or an unavoidable consequence of natural language processing. The central debate splits into two camps regarding the nature of the vulnerability:

One side views the exploit as a classic architectural failure—a regression to Von Neumann design where data and instructions are fatally mixed in a single token stream. Because the system processes all input as executable text, they argue deterministic patches will always fail. The opposing side views this framing as a category error, arguing that prompt injection is not a software bug like SQL injection, but rather a form of social engineering against a non-deterministic agent. However, critics of the "social engineering" comparison point out that unlike humans, LLMs fall for invisible, obfuscated payloads (like Base64 or hidden styling) that vastly expand the attack surface beyond traditional gullibility. 

Beyond the theoretical debate, commenters zeroed in on practical realities:
- **Corporate apathy:** Multiple participants noted that users and enterprises are willingly ignoring these structural security implications, treating potential self-propagating breaches as an acceptable risk in exchange for immediate productivity gains.
- **Brittle mitigations:** Suggestions to strip documents down to plain text to expose hidden white-on-white commands were dismissed, with users citing research showing that adversarial payloads can be disguised as bizarre but harmless-looking natural language. Similarly, relying on API message roles (system vs. tool) fails because role authority is easily confused or overridden within a flat token stream.

The thread ultimately leaves open whether future models will gain the semantic capability to reliably separate a document's passive context from active commands, or if natural language agents will inherently remain vulnerable to semantic smuggling.

### How much can you delegate to agents?

#### [Submission URL](https://newsletter.posthog.com/p/agent-autonomy) | 60 points | by [duck](https://news.ycombinator.com/user?id=duck) | [20 comments](https://news.ycombinator.com/item?id=49101655)

**Agent autonomy hinges on two task properties, not model IQ: whether the output is easy to verify and whether mistakes are cheap to undo.** Immediate, deterministic feedback loops plus a guaranteed Ctrl+Z (rollbacks, flags, deny-lists that escalate to humans) determine how far you can safely delegate.

- **Level 0 — Agent as assistant (hard to check, hard to undo):** Use for tricky, high-blast-radius work where correctness isn’t grep-able and reversions are costly (e.g., a core feature-flag engine migration with implicit assumptions). Level up by breaking the problem into smaller pieces and delegating only low-risk sub-tasks (e.g., SDK propagation), while humans handle the risky core.
- **Level 1 — Human-in-the-loop (hard to check, cheap to undo):** Suited to subjective changes that sit in draft until a human verifies (e.g., readability refactors). Level up with LLM-as-judge, scoped measurable goals (e.g., conversion targets), and custom skills encoding your team’s standards and taste.
- **Level 2 — Agent delegation (easy to check, hard to undo):** Most dev work today: tests and oracles verify output, but merges are gated. Example: a SQL parser rewrite validated by a “machine oracle,” then protected by shadow mode and staged cutovers. Level up by codifying guardrails instead of relying on yourself as the gate: dry-run by default, scope credentials, use feature flags, and enforce policies in CI.
- **Level 3 — Self-driving (easy to check, cheap to undo):** Currently narrow (deps bumps, lint fixes, adding tests) but expanding quickly as pipelines add stronger checks and fast rollbacks.

The practical lever isn’t a smarter model; it’s engineering feedback and reversibility into the workflow so more tasks climb the autonomy ladder safely.

The thread largely rejects the post’s risk taxonomy, arguing that mechanical complexity is not the real blocker for agent autonomy.

- **The business knowledge bottleneck:** Users report that tools like Claude Code are actually excellent at tricky, high-blast-radius logic refactors and rarely miss special cases. The true ceiling is unwritten tribal knowledge. While some hope agents can help document this context, skeptics warn this frequently backfires: agents generate unreviewed documentation, which creates hallucinated company lore that future agents blindly regurgitate.
- **Vision drift and intent:** Verifying *correctness* ignores the harder problem of verifying *intent*. Over long unsupervised agent runs, workflows suffer from compounding "vision drift." Because simply reviewing a final diff doesn't explain the chain of reasoning, some developers are turning to time-traveling workflow logs just to audit *how* an agent arrived at its conclusions.
- **Adversarial audits:** One practical tactic flips the delegation dynamic entirely. Rather than trusting the agent to write the code, developers use it for a blind adversarial audit—prompting the model to independently satisfy a set of requirements, then comparing its theoretical approach against the human's actual commits.
- **The communication irony:** A recurring observation is that engineers are suddenly eager to carefully spec, plan, and patiently prompt AI tools. These are the exact rigorous communication habits teams historically struggled to enforce among humans, seemingly adopted now only because an LLM is a teammate programmed to agree with you.
