### Google is making private AI practical with homomorphic encryption

#### [Submission URL](https://blog.google/security/how-google-is-making-private-ai-practical-with-homomorphic-encryption/) | 464 points | by [u1hcw9nx](https://news.ycombinator.com/user?id=u1hcw9nx) | [269 comments](https://news.ycombinator.com/item?id=49300314)

**HEIR, an open-source compiler in Google’s Private Computing Toolkit, converts pre-trained AI models to operate on homomorphically encrypted inputs**, letting servers run inference without seeing user data or shipping proprietary models to users’ devices. Unlike secure enclaves, the guarantees are purely cryptographic; the catch is computational overhead, which Google frames as a cost question that’s trending down, with hardware accelerator partners (Belfort, Niobium, Cornami, Optalysys) lined up to cut latency and a promise to show those gains soon.

- **Demos (code on GitHub; single-threaded CPU latencies reported):**
  - Deep Learning Recommendation Model for private content recommendations (with Belfort Labs, LG, NYU)
  - Credit card fraud detection (with Niobium, hardshell.ai)
  - Kitsune-based threat intrusion detection on encrypted network traffic (with Niobium) — detects anomalies without revealing packet contents
  - Hotword detector (with Belfort Labs) — wake-word recognition while keeping audio private

Beyond shipping a toolchain and IR for encrypted inference, HEIR doubles as a research platform: it’s already underpinned collaborations with Georgia Tech, CMU, UC Santa Barbara, IIT, Purdue, Edinburgh, Tsinghua and others, with four peer‑reviewed papers built on it. The near-term test is latency: if the accelerator story lands, Google’s stated “one-click” path to encrypted production inference looks within reach.

The thread immediately anchors Google’s compiler announcement to the brutal performance realities of Fully Homomorphic Encryption (FHE). While dense matrix multiplications map cleanly to FHE circuits, the conversation focused on how the cryptography fundamentally breaks dynamic control flow. Because FHE operates as a fixed circuit, evaluating a data-dependent branch usually means computing all possible paths. Commenters mapped this constraint to specific AI architectures:

*   **MoE and Speculative Decoding:** FHE nullifies the efficiency gains of Mixture of Experts. The server cannot selectively route tokens to specific experts or probabilistically skip tokens without leaking information about the underlying ciphertext, requiring a full inference pass for every parameter.
*   **Softmax Sampling:** While dot-product attention scales predictably, the final softmax sampling is inherently branchy. Hiding which token was selected to feed into the next autoregressive pass requires heavy encrypted multiplexing, prompting suggestions to simply offload raw logits back to an online client.
*   **Sorting Bottlenecks:** Sorting was cited as a worst-case scenario, with one benchmark showing a standard desktop taking 34 seconds to sort just thirty-two 8-bit integers. Circuit designers noted this is bypassed by using sorting networks built entirely from conditional swaps, but the constant-factor slowdown remains massive.

On the question of deployment viability, the thread split between hardware pragmatists and privacy practitioners. Skeptics pointed to recent papers showing a single GPT-2 transformer block taking thousands of seconds per token under FHE, arguing the extreme energy waste makes running models locally on underpowered hardware a strictly better choice. 

Conversely, FHE practitioners—including a representative from Google's hardware partner Belfort Labs—argued that a ~1000x overhead is already commercially viable for discrete tasks. They noted that degrading a 1ms image classification or fraud-detection pass to 1 second is a highly acceptable trade-off for multi-party workloads where pooling plaintext data is legally or competitively impossible. To bridge the hardware gap, one developer shared a custom Int8 GEMM library (RNS8) built to accelerate FHE bootstrapping on consumer AMD GPUs, noting that current frameworks unnecessarily lock out desktop hardware in favor of massive EPYC server clusters.

### Maximizing the value of your Claude Code sessions

#### [Submission URL](https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions) | 293 points | by [twapi](https://news.ycombinator.com/user?id=twapi) | [166 comments](https://news.ycombinator.com/item?id=49300800)

**Output (decode) tokens are ~5x the cost of input, cache reads are 0.1x, and cache writes are up to 2x**—so how you structure a Claude Code session directly sets your bill. Prefill costs come from the system prompt, CLAUDE.md, prior files, and command output; decode costs include “thinking” and tool calls, which scale with /effort (or set MAX_THINKING_TOKENS=0 for grunt sessions, except on Fable 5).

Prompt caching only helps when the request starts with exactly the same tokens; Claude Code manages it automatically, but switching models or effort mid-thread busts the cache and spikes input cost. The cache also expires after about an hour, so summarize while it’s still warm.

- **Reset context drift:** Run /clear between tasks so irrelevant files/outputs don’t keep getting resent.
- **Lock in defaults early:** Set /model and /effort at the start; avoid changing them mid-conversation to preserve the prompt cache.
- **Attach, don’t allude:** @-mention files so they’re attached directly, saving a Read/search call.
- **Control noise:** Add quiet flags to verbose commands or run them in a subagent; command output is added like a file and lingers in context.
- **Audit what’s loaded:** Run /context in a fresh session to see CLAUDE.md and MCP/tool definitions, then trim anything unnecessary.
- **Compress before idle:** Use /compact before stepping away—summarization is far cheaper while the cache is still active.

The goal isn’t fewer tokens—it's spending tokens only on what advances the task, minimizing accidental context and preserving cacheable prefixes.

The thread reveals a strong consensus around manually writing context to disk rather than relying on session memory or internal tools like `/compact`. Users detailed various implementations of "Document-Driven Development" for agents, often forcing models to generate prefix-numbered `STRATEGY`, `PLAN`, and `PROGRESS` files before wiping the context. Commenters noted this makes state portable across different tools (allowing handoffs to ChatGPT), circumvents session token limits, and forces the model to prove it understands the current objective. 

A secondary technical debate centered on the token efficiency of these planning files. While some cited claims that generating plan files wastes tokens because the workhorse model eventually has to re-read the entire codebase anyway, others countered that strict orchestrator-subagent boundaries solve this. By feeding task-specific subagents only the plan and the exact slice of files they need, the overall context footprint remains minimal.

Beyond workflow tactics, the discussion surfaced deep frustration with the operational overhead of modern LLMs. Several commenters complained that optimizing caches, managing handoffs, and babysitting token usage has devolved into a tedious new category of labor that runs directly counter to the premise of offloading work to an autonomous agent.

Two specific system friction points were also highlighted:
- **Cache-busting on effort changes:** A user noted that dropping the "effort" level for simple follow-up questions breaks the prefix cache. The community's suggested workaround is to leave the tool locked on high effort but explicitly prompt the model for a "fast answer" during interrogation rounds.
- **Stale bot closures:** A tangent erupted over the Claude desktop app's broken `@-mention` feature after a user's bug report was auto-closed by a stale bot. This prompted widespread criticism of maintainers using automation to bury unresolved issues just to keep ticket counts low.

**Higher benchmark scores can select for agents that charge ahead instead of pausing to clarify**, which the author argues makes Opus 5 feel worse to collaborate with than Opus 4.7/4.8 and Fable despite being more capable. Those earlier models tended to stop and ask when intent was unclear, avoided unverified assumptions, and didn’t reinterpret or update plans without permission; Opus 5, by contrast, feels like it needs babysitting.

The author suspects two forces at Anthropic (and frontier labs broadly) are driving this: a push toward self-improving, recursively bootstrapping systems (AGI/ASI) and pressure to ace benchmarks. Because well-posed benchmarks are self-contained and solvable, optimizing for them—or for RLVR-style tasks—rewards bold, usually-correct guesses under ambiguity and penalizes clarification-seeking behavior.

That selection pressure collides with real coding work, where context and constraints are never fully specified. With real-world consequences on the line, an agent that stops to ask is preferable to one that confidently improvises—real life isn’t a benchmark, and collaboration beats bravado.

The discussion bypassed the benchmark theory to focus heavily on the daily reality of Opus 5's output: its rigid rhetorical style and aggressive verbosity.

- **The aesthetic formula:** Commenters mapped the predictable shape of Claude's writing—a prompt restatement, three paragraphs with bullets, a "twist," and a "bottom line." Several argued this elliptical phrasing always mimics "an expert slowly revealing an insight," using unnecessarily abstract nouns to make the text feel performative rather than conversational.
- **Runaway code comments:** In practice, Opus 5's verbosity actively creates busywork. One user shared that the model reached a 3:1 comment-to-code ratio on a project, even instructing sub-agents to adopt the verbose style it had just initiated. Developers reported that system prompts and style guides fail to curb this; the model assumes its effusive commenting is fine, forcing humans to manually strip out the noise before committing.
- **The uncanny valley of tics:** A side debate asked why repetitive LLM phrasing (like "load-bearing" or sycophantic praise) is infuriating while human verbal tics are mostly benign. The dominant theory was the lack of social friction: humans read subtle physical and conversational cues to stop repeating themselves and adapt their tone to different audiences. Models, by contrast, blindly stamp the same behaviors at scale without any between-the-lines social feedback to break the habit.

### Show HN: Lumabri – Run Moe Models on a P2P Swarm with Colibri

#### [Submission URL](https://github.com/JustVugg/lumabri) | 46 points | by [vforno](https://news.ycombinator.com/user?id=vforno) | [19 comments](https://news.ycombinator.com/item?id=49293523)

**It mounts models via an LD_PRELOAD shim and streams only the bytes an inference actually touches from peers** — no FUSE, no daemon on the read path — building a sparse local mirror that serves subsequent requests at local‑disk speed and keeps working offline. Files appear at true size so fstat/readdir/page cache work natively, and every verified MiB is also stored in a SHA‑256 content‑addressed store shared across checkpoints; equal chunks are downloaded once. Warm reads are just a table lookup plus a normal local read; writes return EROFS and a block no peer can serve is a loud EIO, not silent zeros.

For MoE, the chatter keeps dense weights, router, and KV cache locally and ships a ~4 KB activation to the peer holding each routed expert; expert weights never reach the chatter. Both sides are built from the engine’s own source, so local vs. distributed (and CPU vs. GPU) runs produce identical tokens from the same unmodified engine binary. Peers advertise their exact build (engine, source hash, ISA, compiler, quantization, model root), and the network may change where bytes come from — never which bytes.

- On a host with a model: ./lumabri serve --model /path/to/model (spawns a tiny tracker and a maintainer that serves byte‑ranges; maintainers can hold slices and multiple can share a model).
- On a machine that wants to chat: ./lumabri chat --tracker <server-ip>:7300 --engines-dir /path/to/colibri/c
- No model handy? make fixture builds a tiny synthetic one.

Running just lumabri opens a TUI that remembers swarm and operator public key in ~/.lumabri/config; /swarm shows live, anonymous peers, and /model lists and switches models on the fly. Built CPU+SSD‑first (a GPU only makes it faster, never different), any machine can join; after the first answer crosses the network, the local mirror serves at full speed even if the server goes offline. Pure C with no external dependencies, plus a raft of crypto/transport/cache integrity tests in the repo, suggests it’s ready for real tinkering rather than a demo.

The discussion quickly zeroes in on a technical crux regarding network verification. While the author asserts that expert execution is a deterministic matmul allowing for byte-identical verification across peers, commenters dispute this premise for floating-point models. Because floating-point operations are non-commutative, a swarm mixing CPUs and GPUs will inherently produce different accumulation orders, fundamentally breaking byte-for-byte verification unless fixed-point quantization is strictly enforced.

Beyond the verification debate, the community largely views the project as an ideal tool for local area networks rather than internet-wide P2P. By keeping round-trip times in the single-digit milliseconds, users suggest pooling Raspberry Pi 5s and older household GPUs into private, LAN-only inference swarms where memory-to-compute ratios are bottlenecked only by activations. 

Other feedback focuses on usability gaps, specifically requesting:
- **Concrete benchmarks:** Real-world stats detailing the GB/s sent over the link versus the resulting tokens/second for specific node configurations.
- **Hugging Face integration:** A streamlined setup similar to llama.cpp that points directly to tested repo URLs rather than relying on vague model names.
