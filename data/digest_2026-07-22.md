### GigaToken: ~1000x faster Language model tokenization

#### [Submission URL](https://github.com/marcelroed/gigatoken/) | 591 points | by [syrusakbary](https://news.ycombinator.com/user?id=syrusakbary) | [116 comments](https://news.ycombinator.com/item?id=49010167)

**Benchmarks hit 24.5 GB/s on dual‑socket EPYC for GPT‑2 (≈989× over HF Tokenizers, 681× vs tiktoken)**, and 8.8 GB/s on an M4 Max (up to 1,268× over HF), by letting a Rust core stream files directly and parallelize across cores. It targets “GB/s tokenization” across most common vocabularies (GPT‑2, Llama 3/4, Qwen, Phi‑4, OLMo, GLM, Gemma, Mistral, CodeLlama, etc.) and multiple CPU classes (AMD servers, Apple Silicon, Ryzen).

- **Drop‑in modes:** wrap an existing Hugging Face tokenizer via `.as_hf()` or a tiktoken tokenizer via `.as_tiktoken()` for minimal code changes. The outputs are designed to match HF exactly in this mode.
- **Fast path:** use the native API (`gt.Tokenizer("Qwen/Qwen3-8B")` + `encode_files(TextFileSource([...], separator=...))`) so Rust reads files directly and maximizes parallelism; passing Python data structures adds overhead.
- **Throughput examples:** GPT‑2 at 24.53 GB/s vs 24.8 MB/s (EPYC); 8.79 GB/s vs 6.9 MB/s and 62.8 MB/s (M4 Max). On a Ryzen 9800X3D, 6.27 GB/s vs 59.0 MB/s and 92.1 MB/s.

The catch: the headline ~1000× gains are with the Gigatoken API; compatibility wrappers still deliver large wins but not the full speedup.

The thread revolves around a structural question about ML pipelines: does a 1000× speedup in tokenization actually matter if GPU-bound generation dominates the runtime? Skeptics argued tokenization makes up less than 0.1% of end-to-end latency and utilizes otherwise idle CPU cycles in GPU clusters. In response, AI platform operators clarified that fast preliminary tokenization is a latency-critical bottleneck for routing, rate-limiting, and budget decisions that must happen before inference even begins. 

The library's author backed this up with practical benchmarks, noting that because GPUs process the initial prompt prefill highly efficiently, CPU tokenization overhead dictates a significant slice of Time-to-First-Token (TTFT). Preliminary numbers showed Gigatoken yielding a 5.5% to 8.4% TTFT reduction for an 8B model on a single B200. 

Behind the benchmarks, the author and peers dissected the specific architectural wins. The massive speedups rely on abandoning outsourced regex engines entirely, executing pretokenization natively with SIMD, aggressively minimizing Python interaction, and heavily optimizing the cache for long-tailed pretoken mappings.
