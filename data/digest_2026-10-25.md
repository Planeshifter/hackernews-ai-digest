### SIMD-accelerated computer vision on a $2 microcontroller

#### [Submission URL](https://shraiwi.com/blog/simd-fast-esp32s3/) | 146 points | by [zdw](https://news.ycombinator.com/user?id=zdw) | [47 comments](https://news.ycombinator.com/item?id=50236681)

**An ESP32-S3 now runs a FAST corner detector at 11.2 MP/s, up from 5.1 MP/s in the reference implementation**, or about 6 ms per QVGA frame. That's enough headroom for a 30fps VGA stream on a roughly $2 chip. (The author calls it a 220% improvement; the numbers work out to about 2.2x.)

The speedup comes from the chip's little-documented 128-bit SIMD instructions, which process sixteen 8-bit pixels per register. The author vectorized the FAST pre-test (sample the four cardinal pixels, require at least three "extreme" ones against a threshold) and wrote a SIMD scoring function too, though the post skips that part.

The ISA fights back in three ways, each with a workaround:

- **No misaligned loads.** The east and west neighbor blocks are extracted from two adjacent aligned registers using the slice-extract instruction.
- **Signed-only 8-bit compares.** Unsigned pixels break when reinterpreted as signed, since 128–255 wraps to -128…-1.
- **Saturating-only arithmetic.** That rules out a plain subtract of 128 to rebias the pixels. The fix is `x - 128 == x ^ 0x80`, because flipping the top bit (place value -128) does the shift. Every load XORs with 0x80 and compares then behave linearly.

Along the way the author wrote **basm**, a basic register allocator for the ESP32-S3 assembly, since hand-allocating vector registers gets painful fast. The post cites only three public SIMD examples (Larry Bank's blog, esp-dsp, esp-dl), so this is relatively uncharted territory, and the XOR trick is the kind of detail that will save the next person hours.

Source code is linked from the post. The benchmarks are the author's own, and the post doesn't detail the test setup, so treat the figures as indicative.

### Attention Is Not What You Need (2025)

#### [Submission URL](https://arxiv.org/abs/2512.19428) | 185 points | by [westurner](https://news.ycombinator.com/user?id=westurner) | [66 comments](https://news.ycombinator.com/item?id=50237224)

**An attention-free architecture built on Grassmann manifolds lands within 10 to 15 percent of Transformer perplexity** on Wikitext-2, but only at toy scale: 13 to 18M parameters, against size-matched Transformers.

The Causal Grassmann layer replaces the L-by-L attention matrix with three steps. It linearly reduces token states, encodes local token pairs as two-dimensional subspaces via Plücker coordinates, and gates those geometric features back into the hidden state. Information moves through multi-scale local windows, and the paper claims linear scaling in sequence length for fixed rank.

The author's framing is that multi-head attention is "tensor lifting" into a pairwise-interaction space. That space is expressive but hard to describe with a small set of explicit invariants, and the Grassmann version is pitched as a more interpretable alternative.

The second result is thinner than it sounds. On SNLI, a Grassmann-Plücker head on DistilBERT scores 0.8538 test accuracy against 0.8511 for a Transformer head. That is a 0.27-point gap, and it comes from swapping the head on a pretrained Transformer backbone, not from an attention-free model.

The caveats are large:
- Only Wikitext-2 and SNLI are evaluated, with no large-scale or long-context results.
- The perplexity result is a deficit, not parity.
- The interpretability claim is argued rather than demonstrated.

It's a single-author, 16KB-source preprint. Treat it as an interesting geometric idea rather than evidence that attention is dispensable, and the title promises much more than the experiments deliver.

The thread's sharpest contribution was a possible causality bug. mapontosevenths read the paper's pairing (z_t, z_{t+Δ}) with positive Δ as feeding future tokens into the gate that updates h_t, which would be leakage. If so, the 10–15% perplexity deficit would be even more damning, since the model would be doing worse despite seeing the future. magicalhippo first read the paper as only pairing t with later positions in a way that stays causal, then conceded the point after checking two reproduction attempts. Both repos use (current, past), i.e. z_t − Δ. They got different results: one was underwhelming, the other roughly matched the paper. The original paper has no code link, and commenters noted it omits many details. Whether the released work leaks remains unresolved.

**Headline vs. evidence.** imtringued argued the framing undercuts itself. A title implying attention is dispensable needs evidence that several architectures match Transformers, as Mamba 3's benchmarks do. A pet architecture that is 10% worse proves the opposite, and a typical ML researcher would move on to the next Transformer-Mamba hybrid. magicalhippo countered with the paper's own claim: what matters is representations moving on manifolds, not attention as such. The authors also say they kept the design minimal (k=2, no global invariants) on purpose.

**Technical skepticism of the Grassmannian idea.** seamossfet said the Grassmannian keeps only subspace orientation and discards the basis of the linear map. That trades information for lower rank. They also asked whether the projection adds MACs that erase the inference savings, and how much more data training would need.

**Does architecture matter at scale?**
- charcircuit said scale is what matters, and that attention-free LLMs work at large size.
- dannyw replied that the scaling laws make efficiency gains equal to more effective compute.
- addag pushed back: sliding-window attention has been around since 2021, and making it match full attention took real ideas, not just compute.
- janalsncm noted that in Qwen 3.5, 75% of layers are linear attention, suggesting a few full-attention layers handle long-range dependencies. hujun236 asked whether the mix is documented and where the full layers sit, since "drop most attention" and "keep some" can both hold.

**Brain tangent.** The thread drifted into whether the brain is just brute force. ngruhn pointed out it runs on 20 watts. Replies offered several explanations:

### The State of Context Engineering

#### [Submission URL](https://www.dbreunig.com/2026/10/24/the-state-of-context-engineering.html) | 251 points | by [pchristensen](https://news.ycombinator.com/user?id=pchristensen) | [63 comments](https://news.ycombinator.com/item?id=50235780)

The author's thesis is that context engineering stays hard because models fail in their own ways: the job is knowing when to be deterministic and when to be probabilistic. This is a lightly edited transcript of his AGNTCon talk, "Context Fails & Fixes," and it doubles as a history of how each new model capability created a new failure mode for harness builders to handle.

The framing story is late 2024's "RAG is dead" moment. Gemini 1.5 pushed windows from ~128K to a million tokens, and Llama 4 Scout shipped 10 million, but inference was a challenge, Scout never caught on, and Meta never followed it up. **Bigger windows didn't remove the need to be selective; they made room for more ways to fail.** He names four:

- **Context poisoning:** a hallucination or bad fact enters the context and the model can't shake it.
- **Context distraction:** the context grows long enough that the model leans on it over its base knowledge.
- **Context confusion:** irrelevant facts, including assumptions about who you are, leak into answers.
- **Context clash:** tool calls, skills, and other harness content conflict with each other.

His best example of poisoning comes from the Gemini 2.5 technical report, where the model played Pokémon. The 1996 Red needs lemonade to bribe a thirsty guard, while the 2004 FireRed remake changed it to iced tea. Gemini, playing the original, kept insisting it needed tea, because the FireRed detail was in its weights. Once tea landed on its to-do list, it spent hours chasing it.

He also keeps ChatGPT and Claude memory off, because it mixes work conversations with personal projects and compounds the confusion.

The excerpt cuts off at the start of the distraction section, so the "fixes" half of the talk, and the promised look ahead, isn't covered here. His book, *The Context Engineering Handbook*, is forthcoming from O'Reilly.

The thread mostly agrees that long context degrades models, then argues about where the threshold sits, why it happens, and how to manage it.

**Organization matters as much as length.** The top comment (BenoitEssiambre) says attention works best when related ideas sit close together, borrowing "dependency length minimization" from psycholinguistics. In his view that explains why progressive disclosure and sub-agents help: unnecessary text pushes relevant pieces apart. His practical tips are to put the most important material at the bottom of a skill, so the thinking block sees it last, and to occasionally repeat a summary of early instructions. darkwater pointed out that this seems to contradict his other claim that models overweight the very start of context. Benoit replied that only a small region at the start is boosted, after which DLM dominates, giving a U-shaped curve. He admitted this came from Claude, possibly sycophantically. ### JetBrains Thinkrail

#### [Submission URL](https://github.com/JetBrains/thinkrail) | 234 points | by [hmokiguess](https://news.ycombinator.com/user?id=hmokiguess) | [170 comments](https://news.ycombinator.com/item?id=50233294)

**ThinkRail wraps the open-source pi coding agent in a full desktop IDE, with each agent task isolated in its own git worktree.** It's JetBrains' bid at an agent-first workbench rather than an editor with a chat sidebar.

The core idea is parallelism without collisions. You open a repo as a project and cut workspaces from it, each with its own branch and directory, so several agents can work at once while your checkout stays untouched. Idle workspaces shelve themselves after the PR merges or closes, or after a quiet week. The topbar tracks branch state against origin and the PR, and can publish, push, open a PR, show CI checks and review status, hand failing checks to the agent, or merge using the repo's last-used method.

The other differentiator is **living specs**: a graph of `SPEC.md` files sits beside the code, and the agent reads, searches, and updates it through dedicated `spec_*` tools. The pitch is that project intent survives between sessions instead of dying with the context window.

Around that:
- Monaco editor tabs, a Files tree with git change marks, terminals, and anchored review comments you can send to a chat as structured context.
- Multiple concurrent pi sessions per workspace, each with its own model and live token and cost readout, plus subagents and a shared editable plan.

The post walks through the arithmetic using the open-source Kimi K3 (69 linear-attention layers, 24 dense layers) as an illustrative case:

- **Sizing:** 3T parameters at 4-bit quantization, split over 93 layers, comes to about 16 GB per layer.
- **Packing:** each dense (full-attention) layer gets its own wafer, with the leftover SRAM reserved for KV cache. Linear-attention layers keep a small fixed-size state per request, so two fit on one wafer. That gives 35 + 24 = 59 wafers.
- **Interconnect:** wafers are chained as a pipeline, passing activations over RDMA over Ethernet at roughly 2 µs per hop.
- **Concurrency:** the pipeline stays full because each stage works on a different request (or micro-batch) at once, so it doesn't run at batch size one. Smaller micro-batches cut per-request latency, larger ones raise throughput.
- **Ceiling:** concurrent requests are capped by the SRAM left for KV cache on the dense-layer wafers. The example assumes 256k-token requests and an 8-bit KV cache.

The design choice that matters is that dense layers, not parameter count, set the wafer bill and the concurrency limit. Linear attention is what makes this mapping cheap. The post says production uses much finer-grained stages than one layer each.
