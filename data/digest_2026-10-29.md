### Building an AI-native engineering org

#### [Submission URL](https://twitter.com/sgondala2/status/2115832070274723875) | 75 points | by [sgondala_ycapp](https://news.ycombinator.com/user?id=sgondala_ycapp) | [85 comments](https://news.ycombinator.com/item?id=50296730)

**Merged changes per engineer are up about 5x since January, with a revert rate under 0.5%.** Sashank Gondala, CTO of FurtherAI, says coding agents alone didn't do it: every time one step sped up, work piled up at the next, so the team rebuilt the whole shipping pipeline one stage at a time between March and September.

The stage-by-stage numbers:

- **Tests:** 91% of changes now include tests, up from 15%.
- **Review:** AI reviews 99% of changes before a human does, up from 60%.
- **CI:** it runs 20x the tests in the same 17 minutes, using parallelization and affected-only test selection.
- **Bug intake:** a Claude-based Slack bot dedupes reports, files tickets and assigns owners. It now files 60% of them.
- **Rules:** tribal knowledge from bugs and review comments becomes small Python checks that fail the build and print the fix. There are 21 so far, and they're a big reason agents can self-correct.
- **Merging:** low-risk changes that pass tests, checks and AI review merge with no human, up to a third of all changes.

Non-engineers ship too. The designer has merged about 50 changes since August, and anyone can ask an agent for a PR from a Slack channel.

The cost was real. Through the summer, customer-facing changes per engineer sat at 17–30 a month while the team invested in tests and tooling. September jumped to 45, and October is on pace for 48. That's closer to 2x than 5x, so the headline merge count and the customer-facing output measure different things.

The second half argues the bottleneck has moved to deciding what to build. In his example, a 10-day feature (3 plan, 6 build, 1 review) gets only 1.75x faster when building gets 3.5x faster, because planning and review rise from 40% to 70% of the time. His answer is to push ownership onto engineers rather than add management layers:

- **Junior:** builds with an agent and can tell when it's wrong.
- **Senior:** plans and reviews their own work.
- **Staff:** takes a vague problem, makes the tradeoffs, and owns the success metric.

Managers are expected to be in the work, for instance trying features on staging as an end user would. The text cuts off before the rest of his manager list. It's a single-company, self-reported account with no outside validation, but the rules-as-code and auto-merge-on-low-risk pieces are concrete enough to copy.

### We ran AI agent swarms in Minecraft and Mindustry

### A tiny world model running games on a Raspberry Pi Pico 2 W

#### [Submission URL](https://github.com/SheepSeb/tinyworldformer) | 268 points | by [airinei](https://news.ycombinator.com/user?id=airinei) | [18 comments](https://news.ycombinator.com/item?id=50295450)

**Two tiny networks on a Pico 2 W play a game that exists only as the first network's predictions:** a looped-transformer world model (26k–131k params) generates each next frame and reward, while a small MLP actor (9k–16k params) picks the action from the generated frame. Neither ever touches the real game code on the chip.

The trick is weight reuse. One transformer block is applied 1–4 times with the same weights, and every pass is trained against the next frame, so loop count becomes a runtime speed/accuracy dial. The Pico runs two loops, costing 2–8M multiply-adds per frame depending on the game. The world model is int8-quantized, and both networks run on the RP2350's core 1 while core 0 handles USB and display.

Exact-frame accuracy on held-out transitions (every cell must match the real numpy game, with frames right after random events excluded) at two loops:
- **Flappy Bird:** 100%
- **Breakout:** 99.99%
- **Pong:** 99.45%
- **Pac-Man lite:** 86.4%
- **Doom-lite:** 83.6%

Doom-lite's number is pessimistic by construction: one misshaded pixel out of 768 cells fails the whole frame. Its loop ablation is the clearest demo of the loop idea, with one pass at 59.8% and two at 83.6%. More loops don't always help, though: Pac-Man peaks at two and Doom-lite at three.

Extras: a streaming RL agent (stream-x) can replace the pretrained actor and learn from scratch on the board, inside its own dream. Any button press hands control to you. The README also lists a browser version and a Rust port directory (`tinyworldformer-rs`), and you can play the real games in a terminal via `uv run python -m tinyworldformer.games.play`.

The catch is scope. These are 20×16 to 48×48 token grids with hand-built games whose hidden state is drawn into the frame, so this shows a world model fits on a microcontroller, not that it generalizes beyond them.

The most substantive exchange was about whether the actor learns to exploit the world model. xpct asked if the actor, trained on the model's mistakes, would learn to force hallucinations. The author (sheepseb) said yes: in Breakout, hitting a corner destroyed more blocks than it should, and in Doom-lite the agent could shoot from miles away and still get a kill. The fix was to add noise to the input frame while keeping the target clean.

Another commenter (noduerme) then probed how the model tracks hidden state such as direction and velocity. The author's answer is that state is encoded explicitly in tokens rather than inferred from the pixels:
- **Doom-lite:** a minimap holds a player token and facing direction. Using only the 3D view was harder to learn from wall patterns, so the agent reads the map and isn't "grokking" position.
- **Pac-Man:** the model goes by mouth direction, with tokens for "keep going" or N/E/S/W.
- **Breakout:** four ball tokens, one per diagonal, and the ball moves one cell per step.
- **Pong:** six ball tokens, combining up/level/down with left/right.

This ties back to the submission's caveat that hidden state is drawn into the frame.

Other points from the thread:
- **Single model vs. per-game models:** andai asked if one model covers all games. svantana inferred from the differing parameter and MAC counts that each game has its own model, and said a single world model that could dream up games between the training games would be far more impressive. The author confirmed each game has a self-contained net, said train and validation data don't overlap, and thinks merging them would be easy.
- **Training hardware:** the world model was trained on an RTX 4060. The actor learned on the Pico itself using stream-ac.
- **Use in real games:** several people wanted to fold this into a traditional game or use it for procedural generation. The author said an open world would make hallucinations hard to avoid, but that other cases are doable with enough effort.
- **Web and platform:** the author said the core is `no_std` Rust, uses embassy-rs with no OS on the Pico, and can build to WebAssembly but doesn't use WebGPU. jbarberu pointed out that the Pico is a microcontroller running bare metal or an RTOS, so the WebGPU question doesn't transfer.
- **Broader sentiment:** dannyw liked that looped transformers were needed for Doom-lite but not for simpler games. skrellm and Coill see tiny local models as the long-term future of AI, with plenty of optimization headroom left.

### LLM Voice

#### [Submission URL](https://martinfowler.com/bliki/LLM-Voice.html) | 584 points | by [ibobev](https://news.ycombinator.com/user?id=ibobev) | [319 comments](https://news.ycombinator.com/item?id=50290177)

**Martin Fowler argues that the damage from LLM-written prose is the reader's gut reaction, not a detection problem.** He describes an uncanny-valley response, with the desire to read on "atrophying, sometimes to the point of revulsion", that kicks in before any classifier could help. He distrusts AI-detection tools for that reason, and also doubts his own ear, since some "LLM-sounding" phrases ("a new sales motion") are just generational drift in human speech.

His advice to authors is strict:
- Don't have an LLM write a first draft. Even a heavily human-edited one is hard to purge of the voice.
- Don't accept rephrasing suggestions either.
- Outlines are maybe OK, but only as outlines.
- Say your writing aloud in your head before you put it down.

He knows of one fully LLM-drafted piece that read clean, but it took a professional editor at a major periodical to get there.

His strongest argument is about thinking rather than style. Fowler uses writing to work out what he actually understands, so delegating the prose means delegating the comprehension too. He also finds it more worrying if LLMs eventually become indistinguishable.

He grants exceptions:
- **Accessibility:** Jim Highsmith relies on an LLM to keep writing despite Parkinson's, and Fowler will gladly put up with the voice.
- **Translation:** colleagues writing in a second or fourth language, though he'd still take clunky human prose over smooth, soulless output.
- **Machine-facing text:** form letters or reports nobody will read. Michael Nygard's gloss is that you're then communicating with a process, not a person.

On his own site, authors must declare AI use, usually in the acknowledgments. Fowler uses AI only as a search tool and verifies against sources. The essay is opinion with no data behind it, and its "tells" go undefined beyond a joke about "load-bearing tapestries".

The thread mostly skips Fowler's thinking-versus-delegation argument. It centers on why LLM prose reads so badly, and the sharpest split is over whether that is a fixable training artifact or a structural limit.

**Why it reads badly.** BurritoKing, who calls himself aggressively pro-AI, opened with the symptom: everything sounds identical and rambles. He now abandons posts partway and retreats to pre-2023 writing as a filter.

- HarHarVeryFunny argued that a model trained to minimize prediction error will be predictable. RLHF also rewards long, authoritative-sounding answers, which means padding.
- ThrustVectoring added that human rhetorical devices have purposes. "It's not X, it's Y" exists to preempt a misconception the reader is expected to hold, but an LLM emits it in statistically appropriate quantities with no reader in mind. He suspects this needs something like a theory of mind to fix.
- ahartmetz saw the same pattern in code comments. "Not using bubblesort because quicksort is faster" is garbage, while "not doing the obvious thing because of X two modules over" is gold.
- benjamincburns proposed prompt leakage. The model has no separate mental model of the reader, so the prompting conversation spills into the prose. His example was docs that read like "no, make it a control center, not a text box". The docs' author turned up in the replies and agreed. Claude-edited docs only work if you spend enough effort to have written them yourself. zenoprax's fix is to rewrite from scratch and reset context.

**The main dispute: can prompting escape the predictability?**
- HarHarVeryFunny's side holds that the literal objective is accurate continuation, and "good" is only weakly selected through contractor preferences. Asking for "unpredictable and interesting" yields "predictable unpredictability". His chess example is that a model asked to continue a game plays at the level of the player it is imitating, not to win.
- blobbers countered that a model trained on all great prose can be steered by goals. "In the style of Dickens" or "how Magnus Carlsen would win" gets different output, and modern deep attention models are far from a coarse "statistical blend". HarHarVeryFunny pushed back that feed-forward autoregressive models can't truly self-evaluate. That reply was cut off in the thread, so the crux stayed open: does prompting move the model out of its own distribution, or only along it?

**Side threads**
- hxtk cited a study finding that music needs stretches of predictability so it can later subvert expectations. thin_carapace and HarHarVeryFunny extended this to jokes, as setup followed by a surprising payoff.
- Gemini was praised as more readable and direct (jacmilts, mythrwy), but also as the worst flatterer ("I now believe I'm a genius", said api). mythrwy added that it plays looser with facts. FranzFerdiNaN said every model flatters and that overcorrections produce a curt Stack Overflow tone. 3371 told of a former boss who trusted Gemini's flattery and assigned unrealistic work based on it, which he blamed for destroying the company.

The policy takes no side on whether LLMs are good or bad and says the project has no consensus on costs and benefits. It sets expectations for contributions and reviews instead:

- **P1, people and community:** Discussion with reviewers stays human. Using an LLM to navigate the code, translate, or investigate is fine, but generated text can't stand in for the contributor's own judgement.
- **P2, easy to review:** Contributors should put substantially more effort into a patch than reviewers need to understand it. That means a clear goal, an explained design, tests, and small pieces. A patch that compiles but leaves the reviewer to reconstruct the reasoning fails.
