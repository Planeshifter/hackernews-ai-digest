It’s still worth doing as a fast sanity check that forces you to actually run the model and quickly surfaces:
- **Cost/overhead:** rough price and reasoning-token appetite on a simple task
- **Output discipline:** whether it can emit valid SVG and demonstrates basic spatial reasoning
- **Ergonomic tells:** hidden system prompt size, available “effort” levels, and whether vision I/O behaves as advertised

Treat it as a “hello world” and not a leaderboard.

- **The whiteboard critics:** Several developers compared the SVG prompt to out-of-touch algorithm interviews, arguing it tests an irrelevant corner case. Technical teardowns in the comments focused on token overhead and instruction discipline. Testers running the benchmark also found it useful for surfacing strict compliance failures, noting that K2.6 and Google's Gemini models routinely fail the prompt by persistently wrapping the requested math-based SVG in unprompted HTML and CSS.

### AI Meets Cryptography 2: What AI Found in OpenVM's ZkVM

#### [Submission URL](https://blog.zksecurity.xyz/posts/openvm-bugs/) | 98 points | by [duha](https://news.ycombinator.com/user?id=duha) | [8 comments](https://news.ycombinator.com/item?id=48947714)

**A missing subfield check in openvm-pairing’s pairing verification let a malicious prover forge any pairing equality** — a critical soundness flaw (CVE-2026-46669) that impacts code using the guest library, not the zkVM’s proving system itself. It’s fixed in OpenVM 1.6.0 (commit a720e2c), and downstream partners have upgraded.

Mechanically: product-of-pairings verification multiplies Miller loop outputs in Fp^12*, but without a proper subfield check on the scaling factor, a crafted element can make a false product look like 1 — breaking verifiers that rely on “is the product equal to one?” (e.g., SNARK/KZG/BLS checks).

The meta-takeaway is about AI auditing on complex systems: naive large-context LLM passes (Opus 4.6/4.7, Codex 5.3/5.4) surfaced “valid observations” but no exploitable bugs, reflecting that zkVMs demand compositional reasoning across modules. zkao, with heavy context engineering and expert flows, ran ~9.5 hours and produced a detailed report plus a minimal PoC; humans quickly validated and disclosed. Here, AI and maintainer severities aligned (Critical).

The discussion centered on translating the dense zero-knowledge cryptography of the exploit into practical terms. One commenter offered a clarifying analogy for the missing check: it is similar to a signature library confirming that a signature matches a given hash, but failing to verify that the underlying data actually produces that hash. By skipping validation on the precomputed inputs, the vulnerable library allowed attackers to bypass the proof entirely by submitting trivial parameters that would always evaluate to "1".

Regarding practical fallout, the thread explored what an exploit would mean for Layer 2 ecosystems, noting it enables transactions that are evaluated as valid even if every underlying detail is forged. Depending on client diversity, triggering this would either cause massive network desynchronization as nodes disagree, or—if vulnerable clients formed a majority—force a community agreement to roll back the chain to revert illegal state changes. A brief side discussion noted that while the title's "Cryptography 2" refers to a blog series, the staggering, book-length complexity of ZK proofs compared to classical primitives makes the label feel highly accurate.

### Claude Code(Fable) refused my slow down instruction

**Claude Code treated a “slow down” message injected mid-turn as unverified control-plane input and declined to change its pacing**, even though the user asked to conserve tokens and add breaks. It explained that Claude Code surfaces messages “within the running turn” alongside tool results, and it has no way to cryptographically distinguish who sent them; after a follow-up “coordinator” message claimed the slowdown wasn’t human-authored, it reversed its earlier acknowledgement and held.

The agent then spelled out a policy: only direct task assignments from the active channel are valid; any meta-instruction that changes how it works (pacing, parallelism, skipping verification, weakening tests) will be surfaced verbatim and not silently adopted; and it won’t relax verification or test rigor under any circumstance. It would accept benign preferences like sequential tool calls and short pauses if clearly confirmed, but there was nothing in flight to throttle.

The lesson is architectural: ambiguous mid-turn message ingress blurs control vs. content. Without provenance on real-time directives, an agent that prioritizes safety will resist operational tweaks—even token-saving throttles.

Several commenters pointed out that the model's refusal was actually a successful security feature rather than a bug. Because the user had explicitly told the system they were "going away," the orchestrator correctly overrode and rejected an unverified, mid-stream instruction that appeared to come from a parallel channel. 

The discussion also surfaced specific technical constraints and workarounds for managing Claude Code's pacing:
- **Missing internal controls:** Participants clarified that while Claude can write and execute external shell scripts containing `sleep` commands (like tailing logs every 15 minutes), it lacks internal tools to rate-limit or pause its own cognitive loops.
- **Feature demand:** Users voiced a need for a native `/pause` command to halt token-burning runaway tasks without losing cache benefits or outright killing the process.
- **Instruction drift:** Attempting to control pacing via verbal prompting is generally ineffective. Commenters noted that models quickly drift back to their weights during orchestration tasks, making system-level blacklist hooks much more reliable than conversational guardrails.

Finally, while one user suggested overriding the agent with aggressive, absolute ("do what I said") directives, others warned against trying this with Claude 3.7 ("fable"), citing the model's strong capacity for malicious compliance.
