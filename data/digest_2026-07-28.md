### Kimi K3 Architecture Overview and Notes

#### [Submission URL](https://sebastianraschka.com/blog/2026/kimi-k3-architecture-notes.html) | 487 points | by [ModelForge](https://news.ycombinator.com/user?id=ModelForge) | [104 comments](https://news.ycombinator.com/item?id=49085698)

**Scaled from 48B to 2.8T parameters, K3 is currently the largest open‑weight model**, and the architecture reads like a production‑scaled Kimi Linear with targeted efficiency swaps rather than wholesale redesigns.

- **LatentMoE**: replaces standard MoE (as in Nemotron 3 Ultra) by down‑projecting large linear layers, conceptually similar to multi‑head latent attention, to cut inference cost.
- **Attention stack tweaks**: regular attention is swapped for multi‑head latent attention and Kimi Delta Attention to further improve inference efficiency.
- **Attention residuals (not just an efficiency tweak)**: residuals are connected across layers with attention‑weighted contributions (already in Kimi Linear), yielding small but consistent gains in validation loss and downstream metrics at ~4% extra training cost and ~2% extra inference cost; contrasts with DeepSeek V4’s mHC which widens the residual path instead.
- **NoPE everywhere**: RoPE is removed entirely in favor of No Positional Embeddings across all layers; unlike mixed schemes elsewhere, this is, per the note, the first frontier‑level model to go all‑in on NoPE.
- **Native multimodal support**: added alongside the architectural changes.

### A walk through of the DeltaNet family of linear attention variants

#### [Submission URL](https://blog.doubleword.ai/you-could-have-come-up-with-kimi-delta-attention) | 294 points | by [AnhTho_FR](https://news.ycombinator.com/user?id=AnhTho_FR) | [125 comments](https://news.ycombinator.com/item?id=49085909)

**Treating attention as a fixed-size value-by-key map S_t and making each write correct the predicted value along the current key** yields Kimi Delta Attention as an error-corrective linear memory with decay and gating. Starting from softmax attention, the post first drops the softmax to expose linear attention as a recurrent outer-product state S_t = Σ_i |v_i><k_i| with reads o_t = S_t|q_t>, which is linear-time but loses normalization and selectivity. The key failure is “addition is not assignment”: after a write, querying with the same key returns v_t plus whatever the old state already produced, motivating a delta-style update.

- Softmax → linear attention: consolidate history into S_t ∈ R^{d_v×d_k}, updated per token by adding |v_t><k_t|.
- DeltaNet: make writes enforce S_t|k_t| ≈ |v_t> by predicting v̂_t = S_{t-1}|k_t> and writing the error e_t = β_t (|v_t> − |v̂_t>), then S_t = S_{t-1} + |e_t><k_t| (with normalized keys to control scale).
- Gated DeltaNet: introduce a forget/decay gate on the previous state via per-dimension α_t, shaping capacity and stability.
- KDA (used in recent Qwen/Kimi models): S̃_t = S_{t-1} Diag(α_t); v̂_t = S̃_t|k_t>; e_t = β_t(|v_t> − |v̂_t>); S_t = S̃_t + |e_t><k_t|; read o_t = S_t(d_k^{-1/2}|q_t>). The mechanism is a selective, gated delta write on a decayed state.

The piece sticks to bra–ket notation to make the shapes explicit and closes with recurrent and chunkwise Triton kernels that implement the updates, framing linear attention as an online associative memory where gates and normalization do the heavy lifting.

The thread immediately polarized over a fundamental "APL-versus-Fortran" debate regarding the legibility of mathematical notation in machine learning. One camp argued that single-letter variables and positional operators turn ML papers into impenetrable "CodeGolf," advocating for Python-style pseudocode and explicit typing to lower the barrier to entry. The opposing camp countered that mathematical terseness is essential for pattern recognition. They argued that dense notation explicitly offloads cognitive work to the brain's visual system and highlights structural symmetries, whereas verbose variable names introduce comprehension-destroying visual noise and an unnecessary English-language bias.

Regarding the submission itself, readers were split on its accessibility. A commenter with a physics background praised the bra-ket notation for intuitively solving the horizontal-versus-vertical ambiguity of standard vector matrices. Conversely, others complained the author still assumed deep domain knowledge by leaving standard attention variables ($q$, $k$, $S$) implicitly defined.

Specific additions to the discussion included:
- **Delta vs. Quadratic edge cases:** A linked visual derivation illustrated the exact behavioral difference: when given identical keys with different values, quadratic attention simply averages the resulting values, whereas a delta network smoothly updates to the latest value.
- **Variance scaling:** A reader clarified a conceptual step the article skipped over, noting that dividing by the square root of $d_k$ is structurally required to counter variance scaling tied to the matrix's dimension.
- **Monastic mathematics:** A philosophical tangent about insulating future humans from algorithmic homogenization to preserve their capacity for mathematical novelty led to strong recommendations for Neal Stephenson's *Anathem*.

**Keep autograd-friendly PyTorch as the executable spec, generate explicit forward/backward training code with LLMs for production, and prove equivalence with a verifier.** That’s the proposed split: PyTorch plays a dual role as both the reference language and the implementation language, but the optimized path can diverge from the reference as long as it’s validated. The argument mirrors how kernel DSLs are used today: authors ship hand-tuned kernels for peak performance while maintaining plain PyTorch reference implementations to check correctness.

- **Problem:** At scale, autograd’s implicit backward graph hides most compute, making debugging and fusion hard; compiler pattern-matching is brittle.
- **Recipe:** Keep the standard PyTorch training step as the reference; have coding agents/LLMs emit explicit forward–backward code that can be optimized independently.
- **Verification:** Check equivalence via bitwise tests or graph-capture/structural comparison (translation validation). For fused paths, include a reference implementation of the fusion so the verifier can match across fused/unfused forms.

This frames PyTorch as one implementation to research in, one to scale with, and a verifier to bind them—an answer to getting eager-mode control with graph-level conveniences without PyTorch needing to self-disrupt to hit frontier training needs.

The debate centers on whether outsourcing production code generation to LLMs means "giving up" on traditional compilers. One camp argues that compilers have hit a practical wall: they cannot generate maximally efficient code across diverse, heavily constrained hardware targets without modifying the source language, making LLMs a necessary bridge between high-level specifications and low-level operational details. Conversely, others maintain that traditional program analysis remains essential for global optimizations—such as defining kernel boundaries, buffer lifetimes, and parallel scheduling—even if LLMs prove capable at local kernel-level optimization.

Responding directly to the thread, the author (`ezyang`) acknowledged the current existential "malaise" among compiler teams over AI, but argued that in a maximalist AI world, the compiler simply pivots to become a verifier for LLM output. He also defended standard compilers as a critical baseline for non-Transformer architectures and organizations lacking dedicated kernel engineers.

- **The Lingua Franca:** Pragmatists validated the premise of using PyTorch as the reference spec, noting its syntax has effectively become standard pseudocode in ML research (often written out to `loss.backward()`).
