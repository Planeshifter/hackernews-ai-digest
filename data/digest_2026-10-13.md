### Redesigning source control at Anthropic

#### [Submission URL](https://www.anthropic.com/engineering/redesigning-source-control) | 855 points | by [Philpax](https://news.ycombinator.com/user?id=Philpax) | [950 comments](https://news.ycombinator.com/item?id=50073633)

**Anthropic's merge rate went from ~2,500 to over 30,000 code changes per day between May and September 2026, and git stopped scaling with it.** The company's answer was Scion, an in-house version control system that replaced git across the monorepo in five months. The post's framing is that Claude writes code fast enough that source control, builds, and CI are now the bottleneck.

The numbers explain why git broke. Main's history alone is almost 100 GB, and a compressed working copy tops 25 GB. CI does around 25 million checkouts a day, which would mean over 600 PB of naive git traffic. Anthropic tried the standard workarounds (shallow clones, sparse checkouts, promisor remotes, seed snapshots in blob storage) and at peak ran several hundred internal git mirrors. Seeds drifted behind main, and diff and blame on partial clones took ever more care to keep working.

The key insight: nearly every client is an agent or a job that is online by definition, so git's offline, every-clone-is-a-server design was pure overhead. Scion's design follows from that:

- **Always-online clients** that fetch data on demand and keep only a bounded local object cache.
- **A thin client.** The server handles history, blame, commits, merges, and rebases. The client lays out files, watches the filesystem, and computes very little on its own.
- **Every query exposed as an API**, so many jobs need no local repo at all. Anthropic says its automated bisect and revert pipelines wouldn't be practical at scale without this.

The team credits prior art from Google's Piper and Meta's Sapling. Alongside Scion, it shipped a code review surface called Antique, code search, a source control IAM system, and new ways of landing large volumes of reviewed code, all in the same five months. The post also says Claude helped build much of it, which makes the project a self-referential case study.

The caveat is that the workload is unusual, and Anthropic says so itself. Few organizations will hit 30,000 merges a day soon. Scion appears to be internal, with no mention of release in the excerpt, which was truncated before the implementation details.

The thread skipped past Scion almost entirely and turned into an argument about Claude-written code quality and what "engineering" means. The opening complaint was that unreviewed Claude output keeps turning out to be "janky crap", so how does Anthropic operate at this speed?

- The counter-camp, led by a heavy user (6-12 hours a day), says they hit few bugs and asks why a human-written tool would be better. A key question was how a CLI that mostly forwards text to a model could even be noticeably slow. The replies were memory use and rendering.

**"Good enough" engineering vs. excellence**
- One side argues engineering means fitting time and money constraints. Perfect code is wasteful, and users didn't leave Claude Code for better-polished rivals. One commenter bet Anthropic is counting on model improvements outpacing the code's tangledness, and so far it's winning. Another said they have seen the opposite failure, where linter-driven "quality" paralyzes a team.
- The pushback is that nobody has shown the trade-offs justify the current state, and that real users do complain. A reply noted users who complain often have no real alternative. ### How to engineer an AI harness for game development

#### [Submission URL](https://kylekukshtel.com/ai-harness-engineering-game-development-claude-code) | 164 points | by [kkukshtel](https://news.ycombinator.com/user?id=kkukshtel) | [85 comments](https://news.ycombinator.com/item?id=50072120)

**LLMs fail at games because so much of a game isn't code**, argues Kyle Kukshtel, a roughly 15-year game programmer. His claim is that the "LLMs are bad at games" sentiment is structural: models handle web stacks well because everything there is text-readable source, while games have assets, scenes, and other non-code content that is effectively opaque to them.

This is a blog adaptation of his "Your Game Is A Harness" talk from Indie Rodeo in Calgary, written by hand without AI. The excerpt covers his background and the diagnosis. It starts with his moodboarding site mood.site, which he built through blind copy-paste into ChatGPT in about 20 hours over 2-3 weeks, and which he says converted him.

He offers three reasons web beats games:
- Far more high-quality open-source web projects exist to train on.
- Games have "100 other systems" beyond layout and text.
- Much of what a game does is puppeting non-code content.

He reads the Three.js one-shot game trend the same way. Boxy primitives keep everything as code, which suits the LLM but yields slop with no authorial voice beyond the model's median. He also admits a bias: he can spot bad game code easily but can't judge Svelte output as well.

The excerpt cuts off while explaining LLM prompt basics (system, assistant, and user prompts). The actual harness engineering for Claude Code, which the title promises, isn't visible here. The thesis is that the fix is to make your game's non-code state legible to the model.

The thread is mostly a debate over whether a game's last-mile polish can ever be delegated to an LLM. Nearly everyone converges on a middle position: use LLMs for scaffolding and tooling, and keep the taste-driven tweaking human.

**The skeptic case (YesBox, gamedev for five years, who admits to skimming and not using LLMs).** Two arguments. First, the last 20% of polish takes 80% of the time, and editing a field and re-testing beats prompting. Second, an artist's vision can't be fully put into words. Critics countered that he was commenting on tools he doesn't use. Lukan added that sketches and images can be fed to models as input.

**The Candy Crush tangent.** augment_me argued that most players reward cognitive hooks over artistic vision, citing Candy Crush's 13-year run, so craft matters to only a small audience. Replies split several ways:
- xboxnolifes said the "cognitive signals" are the craft: colors, feedback, animation, and tight loops are exactly what set Candy Crush apart from Bejeweled.
- psadauskas gave a concrete example. If a tall candy and a round candy scale by the same 3px when dragged, it can feel wrong in a way you can't articulate, let alone prompt for.
- asutekku noted the game was built by hundreds of people.
- sarchertech noted that most of the top-grossing games look nothing like Candy Crush.
- meheleventyone added that retention and monetization tuning are also detail work, and that human taste still drives it.
- montagg said the post is about making art, and that commercial hits and art can coexist.

**Where LLMs actually help.**
- **Build tools, not tweaks (drusepth).** Have the LLM build the editors and tuning tools that let humans adjust things by hand faster. His team has roughly a hundred of them for one Steam game. d3vnull made the same point: tools that weren't worth building before now are.
- **Prototyping and balance testing (EthanHeilman).** LLM-built AI players and balance tests caught major issues in a game he had mocked up in cardboard. They supplemented human playtests rather than replacing them.

**Authorship.** gen220 compared LLM-assisted work to a Renaissance painting workshop, where the master's imprint survives even though technicians do much of the work. The main risk is keeping enough proximity to the work. demibabs suspected that two people's LLM-built games would end up surprisingly similar. gen220 replied that in interviews where candidates build with an LLM, results diverge quickly according to what each person cares about, leaving the human's "fist."

### Show HN: Parsimony – an open-source benchmark for how much code AI models add

#### [Submission URL](https://parsimony.lasu.dev/) | 76 points | by [lasu](https://news.ycombinator.com/user?id=lasu) | [17 comments](https://news.ycombinator.com/item?id=50077619)

**Parsimony ranks AI coding models by how much net code their patches add**, not by whether they solve the task. It reuses patches already published for DeepSWE, SWE-bench Verified and SWE-bench Live, so nothing gets rerun.

The metric is "coding units": statements, calls, comparisons, names and literals, counted from parsed before/after versions of each changed file. Because it isn't line-based, squeezing logic onto fewer lines doesn't help. Deleted code is subtracted (net = added − removed). Tests, docs and generated files are excluded, and only Python is measured.

The ranking is by mean net units added on solved tasks, lowest first. Pass/fail comes from SWE-bench's published results. Outside scores like the Artificial Analysis Intelligence Index are shown but don't affect rank.

**The caveats are stated up front:**
- Smaller isn't automatically better. Units measure size, not readability or design.
- Models that write more code also tend to solve more (Spearman 0.33–0.60 on boards with 26+ models), so terseness and capability are partly entangled.
- All models use the same agent (mini-SWE-agent), which still influences how much code gets written.

GPT-6 and Claude 5.5 have no public patches, so the author ran them personally on 3–10 DeepSWE tasks using their own subscriptions (Codex, Claude Code, pi). Those show as faded, unranked circles. One cross-check: GPT-5.6 Sol's self-run added 0.88× the code of its published run, a reminder that harness and run variance are real.

You can also load your own benchmark's code-size numbers as JSON and get the same chart in-browser. The author is asking for public patch exports from newer models. Small samples on the newest models mean those points are anecdotes, not rankings.

The thread's main tension is that the metric rewards terseness, and several commenters say terseness is not the same as quality.

**Terse isn't readable.** The top comment says Astra "winning" is a bad signal, since in their experience it plays code golf and writes close to unreadable code. They would rather have Claude's excess comments and tests. Another commenter agrees that too-terse code is as bad as too-verbose code. A third says they are currently in an "Astra season" because they dislike Claude's tone, and wonders whether the two styles will become the tab-vs-spaces split of the LLM era. This is the same caveat the benchmark states, and the thread shows it is not just theoretical.

**Better proxies were requested.**
- One commenter wants real metrics for readable, understandable code, not lint rules.
- Another suggests cyclomatic complexity as a supporting measure, saying AI-written code increasingly suffers from complexity.
- One asks whether less code actually means less review work.
- One liked that measuring at the syntax-tree level strips out comment and formatting noise.

**Does code size matter to AI at all?** One commenter argued that nobody will care how much code an AI generates, because complexity isn't a problem for these systems. Pushback came from experience: agents "Frankenstein" things together at modest scale, and the lack of abstractions hurts anything that must run predictably. The reply was that a well-designed pipeline with some correction beats this. A supporting comment said that style guides, static analysis, formatters, skills and hooks let you get whatever style you want from an agent. This leaves open whether size is a model trait or something you can configure away.

**Smaller threads**
- **Local models:** One commenter wants benchmarks to include the best locally runnable open-weights model (they cited Qwen 3.8 27B at Q4). Another pointed to Artificial Analysis, which filters by size class and open vs proprietary.
- **Reducing agent verbosity:** One person asked how to cut complexity in agent-generated code. They got no direct answer beyond the guardrails advice above.
- **Satire:** A sarcastic exchange argued that benchmarking is an insult to AI's inevitable improvement. The reply was that benchmarks are how researchers improve models.

Dishwasher-loading demos would need dexterous hands (~$10k each), a VLA fine-tuned on teleoperated demonstrations, and an LLM planner on top. #### [Submission URL](https://github.com/watzon/sayso) | 24 points | by [watzon](https://news.ycombinator.com/user?id=watzon) | [10 comments](https://news.ycombinator.com/item?id=50073755)

**Sayso runs speech recognition locally on all three desktop OSes**, using a different native engine on each: WhisperKit and FluidAudio on the Neural Engine for Apple Silicon Macs, transcribe-rs (ONNX Runtime and whisper.cpp) on Windows, and sherpa-onnx on Linux. The app shell is Rust with GPUI. Audio stays on your machine unless you pick a cloud model or a cloud AI style.

The workflow is press a hotkey (Option+Space, Ctrl+Space, or Ctrl+Alt+Space on Linux), talk, and the text is pasted into the focused app with your clipboard restored afterward. Push-to-talk is configurable. A live overlay shows a waveform and the words as you speak.

- **Models:** Parakeet is available on all three platforms. Whisper variants are there too, and macOS adds Nemotron, Canary, Cohere Transcribe, and Apple Speech on macOS 26. Cloud options are OpenAI, Groq, ElevenLabs, Deepgram, AssemblyAI, Mistral, or any OpenAI-compatible server, using your own key.
- **AI styles:** Each style is one editable TOML file (Clean, Email, Message, Notes, and so on). It runs through an OpenAI-compatible endpoint, the Claude CLI, or the Codex CLI. A shared base prompt strips filler words and honors self-corrections like "no wait, Friday". Styles can switch automatically by app or website, though on Linux that's app-only and doesn't work on GNOME or KDE under Wayland.
- **Safety nets:** If insertion or the AI step fails, the text stays on screen and in History. History keeps transcripts indefinitely and audio for 30 days by default. Settings live in a hot-reloaded `config.toml`.

Install is a Homebrew cask on macOS (Apple Silicon, macOS 14+), a per-user installer on Windows 10/11 x64, and .deb, .rpm, Flatpak, AUR, and a Nix flake on Linux. The macOS DMG is signed and notarized. The README hedges on Windows: if the installer is unsigned, SmartScreen will make you click through.

It's from the developer of Pindrop, and it imports that app's dictations, dictionary, and prompt presets. The Linux feature matrix is the part to read before committing, since Wayland support varies by desktop.

The thread is mostly Handy refugees reporting that Sayso feels faster and works with less fiddling, plus one trust question that the author answered by pointing to the open source license.

- **Comparison to Handy:** Several Linux users (shock, jonquark, rpdillon) said Handy was slow or hard to configure. jonquark found it sluggish on Wayland/GNOME and said Sayso's defaults were responsive on an aging laptop. rpdillon's follow-up was the most detailed field test. He used the Linux AppImage with the default Parakeet model, and his Bluetooth headphones were picked up with no setup. Live transcription worked, and 45-60 seconds of audio came back in under a second. Text insertion also worked in Emacs and on the command line, where other tools had struggled. He called it his new default. dr_kiszonka said Handy worked on Windows but not at all on Fedora, and planned to try Sayso.

- **Trust:** jiehong wondered how many of the many dictation apps are honeypots. The author, watzon, said being FOSS is partly meant to make auditing easy. Nobody pushed further on this.

- **Differentiation:** Asked how it differs from other open source dictation apps, watzon gave four points:
  - The app runs in about 5MB of memory because it uses Rust and GPUI instead of Electron or Tauri.
  - It uses a different native backend on each platform, with WhisperKit on macOS.
  - AI enhancement can run through a local Claude Code or Codex CLI, so many users need no setup.
  - He thinks it looks and feels better, and admitted this is subjective.

  He said the larger goal is to match WisprFlow while being FOSS.

The evidence so far is warm but anecdotal and almost entirely from Linux users. Nobody reported on Windows or macOS, and nobody tested the Wayland limitations the submission warns about.
