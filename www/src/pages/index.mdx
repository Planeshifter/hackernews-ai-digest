### Why Micron Is Suddenly Ditching 4F² DRAM as Rivals Double Down

#### [Submission URL](https://hothardware.com/news/why-micron-is-suddenly-ditching-4f-dram) | 114 points | by [rbanffy](https://news.ycombinator.com/user?id=rbanffy) | [17 comments](https://news.ycombinator.com/item?id=50245014)

**Micron is abandoning 4F² DRAM after "over two decades" of work on a design it says it invented**, and it's doing so while Samsung, SK hynix, and CXMT all push ahead with it. CXMT claims 4F² in server DDR5 RDIMMs by the end of the year.

The case against, from CTO Scott DeBoer on Wednesday's roadmap webinar: 4F² promises a theoretical 33% density gain over today's 6F² cell, but real DRAM density is set by capacitor spacing, not nominal cell footprint. So the gain is small in practice while cost and complexity jump. Note that 6F² vs. 4F² describes cell layout, not process node, which is why the two aren't directly comparable to logic-style node names.

Micron's plan instead:
- **1δ (1-delta):** high-density, yields ramping now, with Boise as a production site.
- **1ε (1-epsilon):** in development, adds advanced wafer bonding.
- **ζÅ and ηÅ:** later planar generations, stretched out using High-NA EUV and new materials.
- **3D DRAM:** the actual destination, with stacked layers of storage cells. That's much harder than 3D NAND because each DRAM cell needs a tall capacitor and a leaky transistor, so the architecture needs a rethink.

This is a cash-and-focus bet. If rivals burn capex on vertical-channel transistors and then stall on capacitor scaling, Micron looks smart. If they ship 4F² economically at scale, Micron cedes density and cost ground in the near term. The roadmap gives no date for when 3D DRAM becomes viable, and that's the part the whole wager hinges on.

The thread opens with suspicion of Micron's framing, then splits into a business-logic debate and a technical aside on what 4F² actually means.

The cost compounds in multi-turn agentic sessions. A malformed call doesn't just fail once; the model keeps building on nonsensical context afterward, so quality degrades across the rest of the session.

The fix is **constrained decoding**, which restricts token generation so output must conform to the tool's JSON schema. vLLM added support recently and exposed it as a server-side flag in 0.31. Ubicloud reports that turning it on gets newer Kimi and DeepSeek models to 100% schema accuracy.

The excerpt walks through the mechanics. An agent harness like OpenCode sends a JSON array of tool definitions (for example `webfetch`, with a required `url`, an enum `format`, and an optional `timeout`). The inference engine wraps that in model-specific tokens, such as Kimi's `<|im_system|>tool_declare<|im_middle|>`. The model then emits a call between special tool-call tokens, and that call has to match the schema for the harness to execute it.

The provided text cuts off before the constrained-decoding details, flag name, and any performance overhead, so those are unknown here. Also note that "schema accuracy" measures well-formed calls, not whether the model picked the right tool or sensible arguments. ### Cross-request KV cache exposure in the GLM-5.3 Workers AI model (155 responses)

#### [Submission URL](https://blog.cloudflare.com/kv-cache-exposure-remediation/) | 177 points | by [wondersky](https://news.ycombinator.com/user?id=wondersky) | [71 comments](https://news.ycombinator.com/item?id=50252159)

**Prompts over 681,280 tokens on Cloudflare's GLM-5.3 deployment could come back with other customers' data in the response.** 155 responses were affected between August 27 and September 9, 2026. Cloudflare found no evidence of deliberate exploitation; the remaining traffic looked like ordinary long-context use.

The root cause was two bugs stacked. Cloudflare configured a 1,048,576-token context window but gave the prefill GPUs' KV cache pool room for only 681,280 tokens. They knew about the mismatch before launch and assumed the engine would error on oversized prompts. It didn't. In SGLang's disaggregated prefill/decode mode, an over-length prompt was marked rejected and swapped for a one-token placeholder, but the request wasn't aborted. Prefill computed the cache for the placeholder and shipped it to the decode node, which saw "transfer complete" and assumed the full prompt had overwritten its pages. It hadn't, so decode attended over stale pages still holding earlier requests' data.

The deeper design issue is that KV cache pages aren't zeroed between requests, a common performance tradeoff, which makes the engine's ownership tracking the only isolation boundary.

**Timeline and fix**
- Gadi Evron of Knostic reported it via HackerOne on September 8.
- Cloudflare reproduced it the next morning and pulled the model within 40 minutes of declaring an incident.
- The model was restored September 9 after two changes.
- **Config:** the prefill pool now holds about 2.04 million tokens, roughly 2x the context window, so valid requests never hit the rejection path.
- **Engine:** rejected requests are now retired at the disaggregation admission queue with their original error, before any allocation or KV transfer. Cloudflare proposed this upstream as SGLang #38704; the maintainers also merged #38935, which rejects such requests earlier.

Cloudflare says no other Workers AI model was affected. The lesson is that sizing the config so the bug can't trigger is fragile. Quantization, tensor parallelism, or a future model version can silently shrink the pool again, so the engine-level fix is the real remediation. The post is published alongside a coordinated disclosure from SGLang.

### SIMD-accelerated computer vision on a $2 microcontroller

#### [Submission URL](https://shraiwi.com/blog/simd-fast-esp32s3/) | 146 points | by [zdw](https://news.ycombinator.com/user?id=zdw) | [47 comments](https://news.ycombinator.com/item?id=50236681)

**An ESP32-S3 now runs a FAST corner detector at 11.2 MP/s, up from 5.1 MP/s in the reference implementation**, or about 6 ms per QVGA frame. That's enough headroom for a 30fps VGA stream on a roughly $2 chip. (The author calls it a 220% improvement; the numbers work out to about 2.2x.)

The speedup comes from the chip's little-documented 128-bit SIMD instructions, which process sixteen 8-bit pixels per register. The author vectorized the FAST pre-test (sample the four cardinal pixels, require at least three "extreme" ones against a threshold) and wrote a SIMD scoring function too, though the post skips that part.

The ISA fights back in three ways, each with a workaround:

- **No misaligned loads.** The east and west neighbor blocks are extracted from two adjacent aligned registers using the slice-extract instruction.
- **Signed-only 8-bit compares.** Unsigned pixels break when reinterpreted as signed, since 128–255 wraps to -128…-1.
- **Saturating-only arithmetic.** That rules out a plain subtract of 128 to rebias the pixels. The fix is `x - 128 == x ^ 0x80`, because flipping the top bit (place value -128) does the shift. Every load XORs with 0x80 and compares then behave linearly.

Along the way the author wrote **basm**, a basic register allocator for the ESP32-S3 assembly, since hand-allocating vector registers gets painful fast. The post cites only three public SIMD examples (Larry Bank's blog, esp-dsp, esp-dl), so this is relatively uncharted territory, and the XOR trick is the kind of detail that will save the next person hours.

### Making My Blog Readable by AI Agents

#### [Submission URL](https://deallocatedobjects.com/posts/making-my-blog-readable-by-ai-agents) | 33 points | by [ingve](https://news.ycombinator.com/user?id=ingve) | [8 comments](https://news.ycombinator.com/item?id=50225443)

**A static nginx blog can serve markdown to agents with one `map` and a rewrite**, no framework needed. Send `Accept: text/markdown` to any post URL (or append `.md`) and you get the post as plain markdown with YAML frontmatter (title, canonical URL, author, dates, description) instead of HTML.

The negotiation hinges on two details. Every response carries `Vary: Accept`, so intermediate caches don't serve HTML to an agent or markdown to a browser. The `.md` responses also send a `rel="canonical"` Link header to the HTML page plus `X-Robots-Tag: noindex`, so Google doesn't treat them as duplicate content.

The rest of the evening's work is mostly generated files:

- **`/llms.txt`**: blog summary, how to get markdown, feed locations, citation preference, and every post with a markdown link and one-liner. A Link header on every response points to it. `/llms-full.txt` bundles all posts into one ~225 KB file, and `/index.md` is the homepage.
- **`robots.txt`**: explicitly allows GPTBot, ClaudeBot, PerplexityBot, Google-Extended and about a dozen others, with `Content-Signal: search=yes, ai-input=yes, ai-train=yes`. The author wants citations; a product site might not.
- **Feeds**: the Atom feed gains summaries and a markdown alternate link, and a new JSON Feed uses a custom `_markdown_url` key per item.
- **Metadata**: descriptions, canonicals, Open Graph/Twitter tags, and JSON-LD (BlogPosting, breadcrumbs, WebSite/Blog/Person) on every page.
- **IndexNow**: a ~30-line script pings Bing on publish. Google doesn't participate, but Bing's index feeds several AI search tools.

The cleanup of 2014-era problems is the most reusable part. Stored descriptions had paragraphs mashed together ("…your app.The RevealWhat do I mean…") and some contained raw `<img>` tags, so summaries are now built from rendered text. `maximum-scale=1` was blocking pinch-zoom and is gone. With no `og:image`, X and Threads grabbed the first image on the page, an old banner, so each post now has a 1200x630 card.

The pitch is that none of it is hard. The post itself is fetchable as markdown with the same curl trick.

The thread's main argument is that the whole exercise may be aimed at readers who aren't there. The top comment cites two log-analysis studies. One found no sign that GPTBot, ClaudeBot or similar crawlers request or prioritize `.md` content, even when it's listed in `llms.txt`. The other covered 50 sites over 200+ days and logged zero `/llms.txt` requests from any major AI user-agent. A later commenter pointed to a third experiment where no bot touched the file in three months.

Anecdotal evidence pushed back only weakly:
- One user said their agent tool (oh-my-pi) once read a site's `llms.txt` during research.
- Another gets the odd attempt on a personal site, but mostly bots just fetch `robots.txt`.

Nobody offered data showing real adoption. The open question is whether `Accept: text/markdown` negotiation works better than `llms.txt`, since it serves interactive agent fetches rather than crawlers. The thread didn't test that.

Two other points came up:
- **robots.txt gotcha:** Groups don't merge. If you give GPTBot or another named bot its own group, it stops obeying `User-agent: *`, so every disallow line has to be repeated in each named group.
- **Ethical objection:** One commenter asked why you'd help AI companies take your writing for free.
