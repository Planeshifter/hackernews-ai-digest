### Pg_vectorsearch: An index that is faster than pgvector's IVFFlat and HNSW

#### [Submission URL](https://github.com/timescale/pg_vectorsearch) | 206 points | by [jascha_eng](https://news.ycombinator.com/user?id=jascha_eng) | [52 comments](https://news.ycombinator.com/item?id=50086165)

**Timescale's alpha Postgres extension claims to beat both IVFFlat and HNSW**, including HNSW at equal recall on a 100M-vector dataset while running on an instance with a quarter of the memory. The README states this but, in the text provided, shows no benchmark numbers, so treat the headline as unverified.

The index is called PRISM. It is IVF-style, but it replaces the flat centroid list with a **hierarchical centroid tree** kept warm in the Postgres buffer cache. Vectors are stored RaBitQ-quantized in posting lists laid out for SIMD distance computation (AVX2, AVX512, NEON). RaBitQ's error bounds let a query rule out candidates that can't be nearest neighbors, so far fewer need reranking against full-precision vectors in the heap.

Query flow, per the README:
- Walk the centroid tree to find the nearest clusters.
- Scan posting lists, using async I/O.
- Filter in two stages: estimate, apply the error bound, then rerank.
- Rerank survivors at full precision from the heap and return the top k.

**Adoption is low-friction.** It ships its own `vec32` (float32) and `vec16` (float16) types. These are binary-compatible with pgvector's `vector` and `halfvec`, so you can install both extensions side by side and run `CREATE INDEX ... USING prism (embedding vec32_l2_ops)` on an existing pgvector column without rewriting the table. Queries keep the same `<->`, `<#>` and `<=>` operators. The README says the planner should prefer PRISM over an existing HNSW index while both exist. Recall is tuned with `prism.nprobe`, where 0 means auto, targeting about 0.95 recall.

The catch is maturity. The project is labeled **alpha, for testing and not production**, and upgrades between prereleases may require dropping and recreating the extension and its indexes. Dynamic updates (inserts, updates, deletes) are supported, but posting-list splits depend on running `prism_rebalance` as maintenance. The index is also sized from the row count at `CREATE INDEX`, so load data first.

The thread splits between adoption-blocker checklists and "why a new index at all?", with Timescale/Tiger Data staff answering most of the latter directly.

**Adoption blockers (top comment).** One commenter listed three hurdles: PRISM caps at 1968 dimensions, the extension needs Postgres 18+, and it is too new to appear on any hyperscaler's managed-extension allowlist. Others pushed back on each.

- **Availability:** one commenter said the version and allowlist constraints apply to any bleeding-edge Postgres extension. Another worried that nobody on managed Postgres can use it. A Tiger employee answered that it is PostgreSQL-licensed, that their pg_textsearch was already picked up by AlloyDB and HorizonDB, and that Tiger Cloud is the managed option.

The mechanism targets folio lookup. The series detects "hot" folios and flags them to delay release until after an RCU grace period. That delay lets the fastpath do more than the folio lookup under RCU, which the kernel has done forever. It can also read the folio's data inside the RCU-protected region, with no refcount taken, as long as the user copy doesn't trigger page faults. ### AI Laser Locking for Quantum Computers: How QuEra Automates It

#### [Submission URL](https://www.quera.com/blog-posts/holding-the-light-teaching-an-ai-to-lock-and-tune-our-quantum-computers-lasers) | 28 points | by [EvgeniyZh](https://news.ycombinator.com/user?id=EvgeniyZh) | [5 comments](https://news.ycombinator.com/item?id=50085302)

**An AI agent (Claude) now relocks QuEra's drifting lasers in seconds with nobody in the building**, replacing a recovery that used to depend on one expert driving to the lab at night. It runs on a dedicated testbed, in control of roughly $0.7M of precision hardware, inside human-set safety bounds.

The hard failure case is a mode hop. After a big disturbance, the Ti:sapphire laser can settle stably into the wrong mode and look locked. Fine actuators can't fix it. Recovery means sweeping the coarse knob past a threshold, easing off to capture the target mode, then verifying against an absolute wavelength reference so a wrong mode is never mistaken for success. Logical-qubit lasers must hold within ±1 kHz or better.

The comparison QuEra draws is with its earlier hand-written recovery script, which took a four-role team (laser engineer, software engineer, algorithms designer, tester) two to three weeks to build. A fixed script only covers the failures its authors enumerated. The agent, working through the Model Hardware Standard (MHS), a standard that began as an Anthropic and HHMI Janelia collaboration, proposes a recovery, tries it on live hardware, reads the result, and refines. It does this continuously and overnight, which lets it harden against hundreds of edge cases.

QuEra also says the agent tuned the lock itself, to a quality level it can prove, and carried that ability to a second operating wavelength in a single run.

The caveats: this is a testbed, not the production machine. Aquila, available through Amazon Braket, already exceeds 99% uptime with conventional automatic relocking. The excerpt cuts off before the actual results, so there are no relock-time distributions or failure-rate numbers to check "seconds" against. It's a vendor blog post, so treat it as a credible direction rather than a benchmark.

The thread opens with a skeptical question: why use AI where a PID loop or PDH lock would do? The laser people who answered said the question undersells the problem.

- **Why PID isn't enough:** A laser engineer (GlibMonkeyDeath) called relocking a "highly-non-linear search problem" that PID only handles once you're already close. Much of the skill is tacit. Operators learn which adjuster is "wonky" and drifts most, some people have "the touch" for alignment, and styles are learned by shadowing and are hard to verbalize. They'd like to see the system deliberately de-tuned and the AI asked to hit a target, and they suspect its relentlessness could make it work better than expected.
- **A correction on what the AI does:** j16sdiz read the article as saying the LLM isn't in the feedback loop. It's used to test and tune the recovery program, and the underlying control problem is multivariable, not a single PID loop.
- **Cheaper hardware isn't a lever anyone can pull:** Replying to the "make it cheaper" suggestion, packetlost (who has worked with neutral-atom QCs) said keeping lasers locked is a "massive pain." Telecom wavelengths are cheap because of mass production, but these machines need unusual, precisely tunable wavelengths with little demand behind them, so price and stability won't improve on their own.
- **Superconducting vs. neutral atoms:** spaqin noted that lasers matter only for ion-trap and neutral-atom machines, while the biggest players use superconducting qubits cooled to near absolute zero. Gaze, who has worked on both, pushed back on the cost framing. Dilution fridges are off-the-shelf, and for about half a million you can have one delivered. A neutral-atom system needs many lasers, which can add up to the same amount. Gaze now favors neutral atoms and thinks outsiders fixate on parts that aren't the hard ones.

The thread's main takeaway is that alignment and locking depend on operator intuition, which is what makes automating them with an agent plausible. Nobody tested the claims, and no one cited relock-time data.
