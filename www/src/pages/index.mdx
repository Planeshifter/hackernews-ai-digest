### Using LLM for confidence scoring is a bad idea

#### [Submission URL](https://rumple.github.io/blog/2026/10/20/asking-llm-for-confidence.html) | 193 points | by [jimauthors](https://news.ycombinator.com/user?id=jimauthors) | [97 comments](https://news.ycombinator.com/item?id=50176082)

**A number an LLM writes when asked "how confident are you?" is just more generated text**, the author argues, not a readout of anything inside the model. It's an opinion piece aimed at agent designers who use self-reported scores to gate decisions.

The argument rests on a forecaster analogy. A trustworthy confidence needs two properties: it reflects how much information the prediction is based on, and it has been checked against outcomes on the same kind of question. Calibration means that of all the times a forecaster said 70%, it rained about 70% of the time. Calibration alone isn't enough, since a forecaster who always says the seasonal base rate is calibrated but useless. Without a written record of forecasts and outcomes, you can't know either way.

An LLM's "0.85" has neither property. Pretraining scores the model on predicting the next token, not on whether its stated confidence matches how often it's right. It learned what confidence scores look like in text, not how to make them track accuracy. The author lists symptoms you can reproduce yourself:

- Ask the same question twice and the number changes (0.85, then 0.7), though the information didn't.
- Rephrase to "Are you sure?" and the score moves with nothing new in the problem.
- If the model has already written "This is clearly the right answer," a high score is the natural continuation, so the number follows the prose rather than the evidence.

The text I was given cuts off mid-list, so I can't say what the author recommends instead. The framing, though, points toward measuring confidence empirically, logging predictions against outcomes per task type, rather than asking the model to self-report. **Omnara runs the agent loop as stateless workers over a Postgres event log**, so an agent is just rows in a database: it survives restarts and costs nothing while idle. The design departs from harnesses like Claude Code, Codex, or OpenCode, which keep one long-lived process and a JSONL or SQLite log. Here each loop iteration (one model call, or the tool calls it produced) runs on whichever worker is free, then commits in a single transaction: model output, tool calls, usage, and the next wakeup land together or not at all. Execution is decoupled from the loop. A small daemon, `omnarad`, runs on any macOS or Linux machine (laptop, VM, container, cloud sandbox) and dials out, so no inbound ports are needed. ### Using Claude to reduce the attack surface of code

#### [Submission URL](https://www.anthropic.com/research/attack-surface-reduction) | 132 points | by [dnw](https://news.ycombinator.com/user?id=dnw) | [89 comments](https://news.ycombinator.com/item?id=50175779)

**Instead of hunting individual bugs, Anthropic pointed Claude at the code an attacker can reach and asked what shouldn't be reachable.** Across 25 open-source projects (5M+ lines in C, C++, Java, PHP, Python), it flagged 493 issues without needing to find a single exploitable vulnerability.

The argument is that patching one bug tells you nothing about the ones left, while shrinking reachability lowers the severity of unknown bugs, including ones already being exploited. The goal is to move code behind a gate: pre-auth to post-auth, 0-click to 1-click, on-by-default to opt-in, or deeper into a protocol state machine.

Claude worked with three lenses:

- **Default configuration:** code reachable in the shipped config that no default feature needs.
- **Configuration interaction:** option pairs that look fine alone but silently disable a security control or leave behavior undefined while the code stays live.
- **Early reachability:** complex, security-sensitive code that runs before authentication, without victim interaction, or before a state transition.

Claude inventoried more than 17,000 config options, 3,842 of them security-relevant. The authors sorted projects into Public (serve anyone), Gated (auth required), and Private (operator's own environment), because what counts as excess exposure depends on which one you are.

The headline result is in the gated cohort. All eleven gated projects had unintentionally reachable code, though never a large share of any codebase. Claude found 93 unnecessary pre-auth surfaces in default configs, 37 places where code ran or state was recorded before authentication, and 61 config combinations that quietly weakened an admin-set pre-auth control. The excerpt cuts off while noting that none of these was immediately exploitable.

That caveat matters. These are hardening findings, not CVEs, so the value depends on maintainers accepting "this shouldn't be exposed" as a fix, and the excerpt doesn't say how many were confirmed or fixed. The post also closes with guidance for applying the same approach to your own code.

The thread mostly ignores the attack-surface technique itself and fights over whether Anthropic can be trusted on security, and whether its safety filters hurt defenders more than attackers.

### PHP2Shell: AI uncovers critical RCE in PHP

#### [Submission URL](https://www.wiz.io/blog/php2shell-php-rce) | 446 points | by [danlark1](https://news.ycombinator.com/user?id=danlark1) | [184 comments](https://news.ycombinator.com/item?id=50180836)

**PHP's core engine has memory-safety bugs that let an unauthenticated attacker read worker memory or run code, no matter which app sits on top.** Wiz Research says every PHP release back to 5.4 is affected by at least one. The patch shipped October 21, 2026, and the bugs are grouped under CVE-2026-109618 and CVE-2026-109619, with severity up to CVSS 9.2.

The root cause is how PHP handles fatal errors, especially out-of-memory conditions. A request that dies unexpectedly leaves corrupted internal state behind, and a later request or worker reuses it. The four demonstrated bugs:

- **Upload-progress unserializer use-after-free:** remote disclosure of worker memory (possibly passwords, tokens, API keys, certificates from other requests), and pre-auth RCE on WordPress, Drupal and Joomla.
- **Fatal-error backtrace use-after-free:** pre-auth RCE on Drupal.
- **OPcache type confusion:** corrupts shared PHP state, with pre-auth RCE shown on WordPress.

Wiz chained these into a single exploit script, php2shell. The named CMSs were only demo targets, since the vulnerable code is in PHP itself.

The AI angle is the real story. The flaws are described as decades old, but exploiting them meant a long chain of steps, adapted to each target's memory layout through repeated testing and debugging. Wiz says frontier models cut that to hours per application. Their argument is that exploit complexity stops being a meaningful barrier once models do the grunt work, so "theoretically vulnerable" increasingly means "practically vulnerable." Comparing it to Heartbleed and Log4Shell is Wiz's own framing, and a self-assessment from the discoverer.

The PHP patch fixes the underlying issue and, per Wiz, eliminates the other tracked and untracked variants in the patched release. Automattic, Akamai, AWS, Cloudflare, Fastly, Google, Imperva, Microsoft and Vercel prepared mitigations for people who can't patch right away.
