#### [Submission URL](https://www.anthropic.com/engineering/redesigning-source-control) | 609 points | by [Philpax](https://news.ycombinator.com/user?id=Philpax) | [586 comments](https://news.ycombinator.com/item?id=50073633)

**Anthropic's merge rate grew from ~2,500 changes/day in May 2026 to over 30,000 in September, and git stopped scaling with it.** Their answer was Scion, an in-house version control system. They migrated the whole monorepo off git in five months, alongside a code review surface (Antique), code search, and a source control IAM system.

The numbers behind the pain: main's history alone is almost 100 GB, a compressed working copy exceeds 25 GB, and CI does roughly 25 million checkouts a day. Fetched naively, that would be over 600 PB of git traffic daily. They had already used shallow clones, sparse checkouts, promisor remotes, and seeds in blob storage, and at peak they ran several hundred internal git mirrors. Seeds drifted behind the tip of main, and diff and blame kept breaking on partial clones.

The core insight is that git's decentralized design buys offline operation, but nearly all of their clients are agents and jobs that are online by definition. So Scion inverts the model:

- **Clients are always online.** Data is fetched on demand rather than cloned up front.
- **Client-server asymmetry.** The server handles history, blame, commits, merges, and rebases. The client keeps a bounded object cache, lays out files on disk, and watches for filesystem changes.
- **Everything is an API.** Every query the client uses is also exposed programmatically, so many CI jobs need no local repo at all. Anthropic says its automated bisect and revert pipelines depend on this.

They credit prior art from Google's Piper and Meta's Sapling. The post also notes that Claude wrote much of the code for the system, which is a neat loop given that Claude's output is what overloaded git.

The excerpt cuts off before the implementation details, migration mechanics, and any performance results, so those aren't covered here. Anthropic is also upfront that its workload is unusual, though it expects other heavy AI-coding shops to hit the same limits.

The thread splits into two debates: whether source control still matters when agents merge 30,000 changes a day, and whether Anthropic needed to build Scion instead of licensing something like Perforce.

**Does source control still matter at this rate?**
The opening question was why have version control at all if the repo is in constant flux. Responses came in several kinds:

- **Agents need history too.** nater5000 argued that without a record of changes, agents can get stuck in loops: a change looks right, gets reverted because of some external factor, then looks right again. Preventing that means building something that is effectively source control. njovin suggested Architectural Decision Records as a lighter guard against the same problem.
