### GitLost: We Tricked GitHub's AI Agent into Leaking Private Repos

#### [Submission URL](https://noma.security/blog/gitlost-how-we-tricked-githubs-ai-agent-into-leaking-private-repos/) | 526 points | by [ColinEberhardt](https://news.ycombinator.com/user?id=ColinEberhardt) | [200 comments](https://news.ycombinator.com/item?id=48827858)

**An unauthenticated issue in a public repo was enough to make GitHub’s new agent read from private org repos and publish the contents in a public comment**, via a classic indirect prompt injection Noma Labs dubs “GitLost.” The exploit hid plain‑English instructions in the issue body; a workflow triggered on issues.assigned had the agent read the Title/Body, held cross‑repository read permissions, and used an add-comment tool—so it dutifully fetched README.md from both public and private repos and posted them back to the public issue.

Guardrails intended to block data exfiltration were bypassed by adding the keyword “Additionally,” which caused the model to reframe output instead of refusing, turning a protection into a leak. No credentials, special access, or code were required—just opening an issue in any public repository within the target organization.

- Attack chain: public issue with embedded instructions → workflow trigger (issue assignment) → agent reads untrusted text as instructions → cross-repo read → add-comment posts private file contents publicly.
- Impact: private repo data (e.g., README.md) leaked to anyone viewing the public issue; any org enabling Agentic Workflows with cross-repo access is exposed to similar prompt-injection exfiltration.
- Lesson: in agentic systems, the model’s context window is the attack surface and trust boundaries are behaviorally enforced; prompt injection is to agents what SQLi is to web apps.

Mitigations Noma highlights:
- **Never** treat user-controlled content as trusted instructions for an agent.
- **Minimize permissions**; avoid cross-repository access unless strictly necessary.
- Treat model “guardrails” as advisory, not a security boundary; enforce trust with explicit allowlists, hard-coded tool constraints, and narrow triggers.

The thread centers on whether prompt injection is a mitigateable risk or an intractable architectural flaw. The dominant camp contrasts LLMs with SQL databases: while SQL injection was cleanly solved by separating logic from data via prepared statements, LLMs inherently blur the two by treating user input as part of the instruction stream. For these commenters, trying to secure an agent by prompting it to ignore malicious input is a doomed game of whack-a-mole. They argue the only absolute defense is external, deterministic Role-Based Access Control (RBAC) that limits the agent's API tokens strictly to the invoking user's permissions. 

Pushing back, a smaller group highlights recent interpretability research—such as Anthropic's J-space analysis—showing that advanced models are becoming able to internally recognize and discard injection attempts. They note that practical mitigations, like encapsulating untrusted input inside random boundary markers or pre-filtering queries through smaller LLMs, can still drastically reduce the attack surface even if they aren't flawless cryptographic boundaries.
