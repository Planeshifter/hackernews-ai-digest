### Using AI to reverse engineer hardware

#### [Submission URL](https://blogs.gnome.org/uraeus/2026/10/15/aiandreverseengineerhardware/) | 242 points | by [ErenayDev](https://news.ycombinator.com/user?id=ErenayDev) | [233 comments](https://news.ycombinator.com/item?id=50104299)

**A Red Hat engineer's AI agent, given a Windows VM and a USB trace tap, went from stuck for months to a working Linux scanner driver in a few hours.** The author's mother's negatives needed a Plustek OpticFilm 8200i, whose newer chipset (Genesys GL128, USB 07b3:1825) had no Linux support. Claude Code alone got nowhere. What changed was giving it a harness modeled on a tweet from Glorious Eggroll: full control of a Windows guest to run the vendor driver while the host captured the traffic.

The method, now extracted into a generic **hw-harness** project:

- Run the vendor's Windows driver in a KVM VM with the real device passed through.
- Capture USB traffic on the Linux host with usbmon, below the passthrough layer, so the guest can't see it.
- Repeat the operation with the Linux driver and capture it the same way.
- Diff the two traces; the differences are your bug list.

For devices with no bus to tap, like an internal MIPI camera, it falls back to Windows-side inspection of INF files, registry data, ACPI tables and device properties. The author argues this is clean-room-ish, since it observes behavior and extracts configuration rather than copying code. That's his framing, not a legal opinion.

Results:

- **Scanner backend:** supports color, gray, infrared and color+infrared at 300–7200 dpi, 8 or 16 bits, with IR dust removal. It ships as a Fedora RPM. He also had Claude write a negative-scanning app, Negative Vibes.
- **Upstream collision:** SANE's genesys backend gained support for the scanner in September 2026, while he was working on his own. Compared against it, his driver resolves the same detail at 3600 dpi and is faster at full resolution (34.6 s vs 54.4 s) and adds IR dust removal. Upstream offers more resolution steps. It's one unit and one frame, so treat it as a single data point.
- **MIPI camera:** reusing the harness, he got kernel and libcamera patches for his laptop's camera in a single day.

Caveat: the author says hw-harness was not used in this form for his projects. It's a generalization of bespoke scripts, so expect rough edges. ### Pg_vectorsearch: An index that is faster than pgvector's IVFFlat and HNSW

#### [Submission URL](https://github.com/timescale/pg_vectorsearch) | 206 points | by [jascha_eng](https://news.ycombinator.com/user?id=jascha_eng) | [52 comments](https://news.ycombinator.com/item?id=50086165)

**Timescale's alpha Postgres extension claims to beat both IVFFlat and HNSW**, including HNSW at equal recall on a 100M-vector dataset while running on an instance with a quarter of the memory. The README states this but, in the text provided, shows no benchmark numbers, so treat the headline as unverified.

The index is called PRISM. It is IVF-style, but it replaces the flat centroid list with a **hierarchical centroid tree** kept warm in the Postgres buffer cache. Vectors are stored RaBitQ-quantized in posting lists laid out for SIMD distance computation (AVX2, AVX512, NEON). RaBitQ's error bounds let a query rule out candidates that can't be nearest neighbors, so far fewer need reranking against full-precision vectors in the heap.

Query flow, per the README:
- Walk the centroid tree to find the nearest clusters.
- Scan posting lists, using async I/O.
- Filter in two stages: estimate, apply the error bound, then rerank.
- Rerank survivors at full precision from the heap and return the top k.

**Adoption is low-friction.** It ships its own `vec32` (float32) and `vec16` (float16) types. These are binary-compatible with pgvector's `vector` and `halfvec`, so you can install both extensions side by side and run `CREATE INDEX ... USING prism (embedding vec32_l2_ops)` on an existing pgvector column without rewriting the table. Queries keep the same `<->`, `<#>` and `<=>` operators. The README says the planner should prefer PRISM over an existing HNSW index while both exist. Recall is tuned with `prism.nprobe`, where 0 means auto, targeting about 0.95 recall.

The catch is maturity. The project is labeled **alpha, for testing and not production**, and upgrades between prereleases may require dropping and recreating the extension and its indexes. Dynamic updates (inserts, updates, deletes) are supported, but posting-list splits depend on running `prism_rebalance` as maintenance. The index is also sized from the row count at `CREATE INDEX`, so load data first.

The thread splits between adoption-blocker checklists and "why a new index at all?", with Timescale/Tiger Data staff answering most of the latter directly.

**Adoption blockers (top comment).** One commenter listed three hurdles: PRISM caps at 1968 dimensions, the extension needs Postgres 18+, and it is too new to appear on any hyperscaler's managed-extension allowlist. Others pushed back on each.
- **Dimensions:** one workaround is to index a truncated subvector and then rerank with a full-length comparison in the WHERE clause. Replies say this only works for Matryoshka (MRL) embeddings, though another pointed to Hadamard-rotated embeddings as a case where it also works reasonably well.
- **Availability:** one commenter said the version and allowlist constraints apply to any bleeding-edge Postgres extension. Another worried that nobody on managed Postgres can use it. A Tiger employee answered that it is PostgreSQL-licensed, that their pg_textsearch was already picked up by AlloyDB and HorizonDB, and that Tiger Cloud is the managed option.

**Why not upstream a PR to pgvector, or extend pgvectorscale?**

The main contributor added that a company wants a different pace, a different architecture, and the freedom to ship alpha software. Others noted that "just send a PR" is rarely easy.
- **pgvectorscale:** its author said the DiskANN-style graph index had unpredictable recall, because parts of the graph could become unreachable, especially on low-dimensional data, and they found no principled fix in the literature. Partition-based indexes with modern compression gave stronger guarantees. One follow-up wanted more detail on the recall failures and asked whether the new index, being memory-oriented, still scales on low-memory machines. That went unanswered.

Answers ranged from one database per client to partitioning, which one commenter called the easy part of the problem. The contributor said multi-column indexes for multi-tenant tables are planned.
