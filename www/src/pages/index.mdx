### Building a Multi-Agent System from Scratch: Architecture Patterns

#### [Submission URL](https://kadhar.dev/blog/multi-agent-systems-from-scratch) | 101 points | by [kadharmfn](https://news.ycombinator.com/user?id=kadharmfn) | [43 comments](https://news.ycombinator.com/item?id=50380658)

**Most agent systems should stay single-agent, and this post says so up front.** The author's dinner recommender (location, weather, and restaurant tools plus a step cap) worked fine as one model, and splitting it would have made it slower and pricier.

The post then lays out three splitting patterns, using that same dinner question throughout:

- **Pipeline:** fixed-order assembly line. Easiest to test, but it turns into the next pattern once step three needs to loop back to step one.
- **Orchestrator:** a lead agent plans, farms out work, and merges results. This is the shape behind "deep research" features, and the failure mode is that a bad plan from the lead poisons every helper.
- **Blackboard:** no boss, agents read and write a shared board. Suits open-ended work like debugging, but it's the hardest to test and the easiest to trap in a loop.

An embedded demo runs the dinner request through each pattern with injectable faults (stale weather data, agents bouncing work back and forth) and a guardrails toggle: a checker at handoffs, a hop limit, and a per-request budget. It's a scripted walkthrough, not live AI.

The strongest material is the failure lessons from Stormwise, the author's Claude-based severe-weather assistant, evaluated on 117 cases from real National Weather Service alerts (write-up on arXiv):

- **Bad data travels as fact.** NWS test alerts got ingested as real warnings, and the model believed them. The fix is validation in plain code at every handoff.

### Mass attempted replication of old findings of LLMs with new models

#### [Submission URL](https://zou-group.github.io/llm-claims-shelf-life/) | 30 points | by [zirkonit](https://news.ycombinator.com/user?id=zirkonit) | [4 comments](https://news.ycombinator.com/item?id=50347766)

**44% of 50 widely cited LLM findings no longer hold in current models**, and another 34% have weakened substantially. Only 16% persist and 6% strengthened. The Zou group reran each claim's original setup across 20 models (eight developers, open and closed, released July 2024 to September 2026), fit a trend line to effect size against release date, and classified each claim by how much of the original effect remains. "Expired" means a fifth of the original effect or less.

**Claims expire fast.** The estimated share expired is 4% at six months after publication, 16% at one year, and 39% at two years. Among the 22 expired claims, the mean time to expiry was 15.7 months (median 14.7).

**What dies and what survives:**
- **Expired:** capability failures that post-training has since fixed, such as letter counting, arithmetic in other bases, facts lost in the middle of long contexts, fabricated citations (55% fake with GPT-3.5 in the 2023 study, now rare), and abandoning correct answers under pushback. Five of nine reasoning claims and six of eleven sycophancy-and-deception claims are expired.
- **Weakened:** the reversal curse, two-hop questions, jailbreak and prompt-injection susceptibility, invented package names, and judges' preference for longer answers.
- **Persists or strengthens:** preference-like behaviors rather than capabilities. These include flattery, judges favoring their own answers, near-identical outputs for open prompts, a left political lean, and answering when they should abstain. Nonuniform random-number generation also strengthened.

Areas that labs optimize in post-training expire fastest. Bias and judgment findings last longest, which suggests that "does the model fail at X" papers age worst and "what does the model tend to prefer" papers age best.

The caveat is methodological: the expiry threshold is a fitted trend across models, so a claim can be marked expired even when some individual models still show a strong effect. The page's own examples also use model names I can't verify, so treat the specifics as the authors' framing. The broader implication is that citing a 2023 LLM paper as current fact is risky unless someone has rerun it.

The thread is small, and it mostly circles one question: do the "expired" capability failures reflect better models, or better scaffolding around them?

- **Fix or workaround?** dwroberts noted that Google's models often write code to do counting tasks even when no one asks. ### Octomind – open-source AI harness that saves your tokens, static rust

#### [Submission URL](https://github.com/Muvon/octomind) | 55 points | by [donk8r](https://news.ycombinator.com/user?id=donk8r) | [39 comments](https://news.ycombinator.com/item?id=50352898)

**It solved 24 of 25 tasks drawn from merged pull requests, versus 19 for OpenCode on the same model at roughly twice the cost**, according to the project's own benchmarks (self-reported, with per-case tables and a reproduction guide in the repo). Octomind is a single Rust binary that wraps any LLM with repo tools (file edit, shell, code search, sub-agents) via MCP.

The pitch is that it can run unattended. Instead of approval popups, which block CI, policy lives in `.agents/guardrails.toml` plus scripts: pre-call guards, post-result hooks, and post-turn validators that run before any model opinion. On top sits a **supervisor model** that keeps the plan, trims oversized tool output to the relevant lines, and rejects a self-reported "done" until evidence checks out. An optional cheap classifier handles yes/no routing decisions, and an optional intent check can block calls that conflict with your request.

The token-saving angle is mostly context management:
- Context is assembled once per user message, not per tool round, which keeps the prompt cache intact.
- Older turns are compressed into summaries that cite content-addressed blocks. Raw messages stay archived, and a recall tool restores them verbatim.
- Lessons are extracted from your own corrections and scoped per project and role. With evolution enabled, recurring ones become skill or guardrail candidates that are shadow-tested and A/B-trialled against a control before going live.

It runs as an interactive CLI, stdin pipe, daemon, WebSocket server, or ACP agent in your editor. Packaged agents install from a tap, for example `octomind run developer:general`. Backends include OpenRouter, Anthropic, OpenAI, DeepSeek, and Ollama, with per-request and per-session spend caps. Non-interactive runs that exceed budget exit with code 75.

The caveat: 25 tasks is a small sample, and the benchmark compares only against one rival harness. The self-learning layer is the most ambitious part and the least proven.
