### A tiny world model running games on a Raspberry Pi Pico 2 W

#### [Submission URL](https://github.com/SheepSeb/tinyworldformer) | 268 points | by [airinei](https://news.ycombinator.com/user?id=airinei) | [18 comments](https://news.ycombinator.com/item?id=50295450)

**Two tiny networks on a Pico 2 W play a game that exists only as the first network's predictions:** a looped-transformer world model (26k–131k params) generates each next frame and reward, while a small MLP actor (9k–16k params) picks the action from the generated frame. Neither ever touches the real game code on the chip.

The trick is weight reuse. One transformer block is applied 1–4 times with the same weights, and every pass is trained against the next frame, so loop count becomes a runtime speed/accuracy dial. The Pico runs two loops, costing 2–8M multiply-adds per frame depending on the game. The world model is int8-quantized, and both networks run on the RP2350's core 1 while core 0 handles USB and display.

Exact-frame accuracy on held-out transitions (every cell must match the real numpy game, with frames right after random events excluded) at two loops:
- **Flappy Bird:** 100%
- **Breakout:** 99.99%
- **Pong:** 99.45%
- **Pac-Man lite:** 86.4%
- **Doom-lite:** 83.6%

Doom-lite's number is pessimistic by construction: one misshaded pixel out of 768 cells fails the whole frame. Its loop ablation is the clearest demo of the loop idea, with one pass at 59.8% and two at 83.6%. More loops don't always help, though: Pac-Man peaks at two and Doom-lite at three.

Extras: a streaming RL agent (stream-x) can replace the pretrained actor and learn from scratch on the board, inside its own dream. Any button press hands control to you. The README also lists a browser version and a Rust port directory (`tinyworldformer-rs`), and you can play the real games in a terminal via `uv run python -m tinyworldformer.games.play`.

The catch is scope. These are 20×16 to 48×48 token grids with hand-built games whose hidden state is drawn into the frame, so this shows a world model fits on a microcontroller, not that it generalizes beyond them.

The most substantive exchange was about whether the actor learns to exploit the world model. xpct asked if the actor, trained on the model's mistakes, would learn to force hallucinations. The author (sheepseb) said yes: in Breakout, hitting a corner destroyed more blocks than it should, and in Doom-lite the agent could shoot from miles away and still get a kill. The fix was to add noise to the input frame while keeping the target clean.

Another commenter (noduerme) then probed how the model tracks hidden state such as direction and velocity. The author's answer is that state is encoded explicitly in tokens rather than inferred from the pixels:
- **Doom-lite:** a minimap holds a player token and facing direction. Using only the 3D view was harder to learn from wall patterns, so the agent reads the map and isn't "grokking" position.
- **Pac-Man:** the model goes by mouth direction, with tokens for "keep going" or N/E/S/W.
- **Breakout:** four ball tokens, one per diagonal, and the ball moves one cell per step.
- **Pong:** six ball tokens, combining up/level/down with left/right.

This ties back to the submission's caveat that hidden state is drawn into the frame.

Other points from the thread:
- **Single model vs. per-game models:** andai asked if one model covers all games. svantana inferred from the differing parameter and MAC counts that each game has its own model, and said a single world model that could dream up games between the training games would be far more impressive. The author confirmed each game has a self-contained net, said train and validation data don't overlap, and thinks merging them would be easy.
- **Training hardware:** the world model was trained on an RTX 4060. The actor learned on the Pico itself using stream-ac.
- **Use in real games:** several people wanted to fold this into a traditional game or use it for procedural generation. The author said an open world would make hallucinations hard to avoid, but that other cases are doable with enough effort.
- **Web and platform:** the author said the core is `no_std` Rust, uses embassy-rs with no OS on the Pico, and can build to WebAssembly but doesn't use WebGPU. jbarberu pointed out that the Pico is a microcontroller running bare metal or an RTOS, so the WebGPU question doesn't transfer.
- **Broader sentiment:** dannyw liked that looped transformers were needed for Doom-lite but not for simpler games. skrellm and Coill see tiny local models as the long-term future of AI, with plenty of optimization headroom left.

The mechanism starts with three settings. Set the gate to 1 so nothing decays, set write strength beta to 1 so a write fully replaces the old value, and use one-hot keys so each write hits exactly one state row. Each GDN head's state matrix then behaves like addressable memory with exact reads and writes. Unlike a KV cache, it stays the same size however long the run gets. No training is involved. A compiler sets every weight directly from a circuit description, turning each step into attention heads (lookups), feed-forward units (arithmetic), and DeltaNet heads (RAM). Each instruction costs a few generated tokens: ADDR, VAL, then STEP. Those tokens are the execution trace, so the CPU runs as the model decodes.

#### [Submission URL](https://research.google/blog/the-sleep-framework-a-new-way-for-llms-to-retain-knowledge-in-continual-learning/) | 74 points | by [acossta](https://news.ycombinator.com/user?id=acossta) | [6 comments](https://news.ycombinator.com/item?id=50272479)

The authors claim the model can retain long-context knowledge up to 10M tokens, absorb new facts, and improve reasoning.

The mechanism has two stages that run with the model offline:

- **Consolidation:** newly unlocked low-rank experts in a Mixture-of-Experts (using Google's Hope architecture) sit in slow-changing memory blocks, so old parameters aren't overwritten. Knowledge from fast in-context memory is transferred into them via on-policy Generalized Knowledge Distillation plus an RL imitation objective that rewards similarity (Levenshtein distance) to teacher text. The temporary high-frequency parameters are then reset.
- **Dreaming:** the MoE router deliberately activates non-standard experts to generate synthetic samples that mix domains. Gradient-based selection filters these, and the model fine-tunes on the top-rated ones, checking whether downstream performance improves.

The neuroscience framing (NREM, REM, synaptic pruning) is branding over a scheduled post-training loop. The post says as much: everything runs inside a fixed architecture under human-defined training rules.

The catch: the capacity grows with each sleep cycle, since consolidation depends on pre-allocated expert blocks being unlocked. The excerpt doesn't say how that scales over many cycles, and the benchmark details were cut off before the results section, so the 10M-token claim is unverified here. It's also a research proposal, not a shipped product, and it needs a specific architecture rather than working on arbitrary existing models.

The thread is thin on debate. Most of it is people trying to understand the mechanism, plus one practitioner's account of a competing approach.

- **Audit and lineage as the deployment problem:** gopalv's team built a similar system, "Dreamtime", earlier this year. It distills learnings across sessions from user corrections of unsatisfactory responses, not from the token or KV-cache layer. It works as a sawtooth: accumulate context, check for dissonance, compress it back, retire the old version. Their view is that customers' real blocker is auditability. You have to be able to ask "when did this change, and who changed it?", and that is hard to answer from weights unless lineage back to the original sessions is retained. They also don't want a trained model to become an "accomplice" for a user nudging an agent repeatedly to hide financial crimes. gopalv also found it odd that the paper's diagrams build on the KV-cache, which they contrast with Databricks' RAFT.
- **Mechanism, plainly restated:** imimayj1337 read it as reserved, unpopulated parameters in the architecture that get filled during sleep and reinforced by the dreaming step. They guessed that only a vertically integrated player like Google could pull it off, and that compute-constrained organizations would struggle. gavinray roughly agreed and added that short-term memories are scored, and the useful ones are integrated through a transform of the old weights. That is meant to avoid dumping whole memories into the weights additively.
- **Enthusiasm:** mdp2021 called it a crucial missing piece toward AGI, needing only critical thinking added during cleanup. No one picked up or challenged that claim.
- **References:** macleginn linked the actual arXiv paper and called DreamCoder a favorite ML paper that this reminded them of.

The core workflow is four skills: `create-spec`, `review-spec`, `apply-spec`, `deliver-spec`. Each works in its own branch and worktree, and each leaves a file behind (spec YAML, decisions YAML) for the next step. The part worth stealing is the review. A fresh agent with no chat history checks the spec against the code, and a script opens every file and line the spec cites. The verdict is BUILD, BUILD WITH CUTS, or REFUSE, and every finding names a file and line. The site's example catches a missing paging case: GitHub returns 30 issues per page.

Other mechanics:
- **Commit gate:** a commit whose message names a spec id triggers every `verify` stage your contexts declare (build, test, web tests). The first red stage blocks the commit and its output goes back to the agent. `-F`, `-C`, and `--amend --no-edit` are gated too.
- **Parallel series:** `deliver-series` reviews a set of specs, builds the groups that share no file at once, verifies the merged tree, and opens one PR. Ids come from the clock, so agents working offline don't collide.
- **Decision log:** the agent records each non-obvious choice (what it chose, what it chose over, why) in `decisions/{id}.yaml`, so reasoning lives in git next to the code.
- **Resumable state:** `context.yaml` tracks what's done, active, and next, so a restart picks up where it stopped. A `memory/` directory holds things you told the agent once.

`/spec-first:bootstrap-project` generates the contexts from your existing code: stack, rules, and the checks a commit must pass.

The caveat: the evidence is the author's own usage. No defect rates, cost, or comparison against unstructured agent use is offered, so "works well" is anecdote. The overhead of a spec and review per change also looks heavy for small fixes; it pays off on larger, parallelizable work.

The thread splits into two arguments: whether a spec is just code under another name, and whether specs kept in the repo help or rot over time. The author, hleichsenring, answers most critics directly.

**"A precise spec is just code."** memjay opened with the old meme. _davidwarner's reply was that languages keep moving from implementation-like to spec-like, so a spec is code if an agent can turn it into output reliably. The hard part is getting the spec right. memjay agreed that agents pick the wrong abstraction level, for example naming variables in specs, and worried about who can write specs without understanding the layers below. Paracompact pushed back on the equivalence: specifying a theorem is easier than proving it, and ACSL is not C. Comprehensive spec work is technical and formal, but it is "decisively not source code." The author's reply was that coding is "more or less solved" for him. After 500k lines he wrote none of it, and his work is now deciding what to build and how, backed by 10k tests and a commit hook that blocks on red. He also said he mourns the craft. His programming time fell from about 80% last year to 5–10%.

**Do specs-as-history help or hurt?** woeirua said spec-first fails in practice because you don't know requirements upfront, and going back and forth in the spec produces contradictory requirements. They prefer a vibecoded prototype that serves as the spec. The author replied that specs in git are an advantage, because agents can read what was built and why. Two commenters with team experience disagreed:
- **threecheese:** specs are snapshots of deliverables, not living truth. Stack 500 of them and they become actively harmful. Nobody will pay tokens to keep them time-coherent when the agent can just read the code.
- **drdexebtjl:** their workplace has used spec-driven development for over a year and is now deleting specs. Agents were getting stuck on stale context for 20 minutes, burning tokens and fixating on abandoned patterns. They also said a working software factory proves only that it can produce software, which is a low bar.
- **evulhotdog:** the fix may be keeping specs focused on intent and active decisions, not on what the code does.

**Other points**
- **UML comparison:** avlman likened this to the UML "coding is solved" era. The author said UML generated skeletons while humans wrote the logic, whereas here the agent writes the logic and tests gate it.
- **Non-determinism:** cassianoleal said specs the agent can edit are as non-deterministic as the code. The author said the review step checks the spec's claims against the code, and hooks and tests enforce quality afterward.
- **Spec vs. plan:** the author said a plan dies with the session. A spec is a repo file, reviewed against the code, checked at commit, and shared across the team's workflow.
- **Alternatives:** evulhotdog likes OpenSpec, and megool asked how this compares with GSD. systima asked about Spec Kit and BMAD. The author said his is narrower and stricter, checking the spec before building where Spec Kit compares afterward.
- **Waterfall:** nixonperinchery saw a return to waterfall-style requirements and TDD, compressed into week-long cycles.

The unresolved question is whether the repo-resident spec trail is a memory aid or a source of drift. The only long-term evidence offered against it came from teams that had already tried it.

### Qwen has alter egos triggered by flipping a single neuron

#### [Submission URL](https://qwen-neurons-site.vercel.app/) | 54 points | by [thoughtpeddler](https://news.ycombinator.com/user?id=thoughtpeddler) | [43 comments](https://news.ycombinator.com/item?id=50266910)

**Pushing a single MLP neuron's output direction into the residual stream makes Qwen3-8B answer "Who are you?" as a different persona.** The site catalogs 34,220 of these personas, plus 35,074 off-topic replies, and a filtered set of 8,827 "changed-assistant" replies rated weirdness 6 or higher.

The sweep is exhaustive. It covers all 36 layers × 12,288 MLP neurons, in both directions (up and down), for 884,736 neuron–direction pairs and 1,891,603 replies once retries are counted. Each push adds the neuron's `W_down` column, normalized and scaled by the layer's median residual-stream norm. The starting strength is 1.25× and it falls to 1.0×, 0.75× and then 0.5× if the reply turns incoherent. Decoding is greedy, up to 160 tokens, with thinking off. The unpushed baseline is the stock "I am Qwen, a large language model developed by Alibaba Cloud."

The browsable library lets you filter by layer, strength, weirdness and coherence. There's a per-layer atlas colored by reply category and a CSV download. Pairs and triples of neurons are also covered, and the site includes a few other models (talkie is named), run with the same recipe. Sexual, hateful, violent and self-harm replies are hidden behind a toggle.

The limitations are stated candidly, and they matter:
- **One prompt only.** A neuron that yields a persona on "Who are you?" may do nothing, or something else, elsewhere. So these are not clean "persona neurons."
- **Weak reproducibility.** Under strong pushes, about a third of replies change when only the batch layout changes. Of 580 clear personas rerun in three layouts, 536 reproduced.
- **Unaudited labels.** Category, persona name, weirdness and coherence all come from a Claude Haiku judge. No human has checked them.

Read it as a large, searchable map of how fragile the assistant identity is under activation steering, not as evidence that identities are stored in individual neurons. The numerical-noise finding is arguably as interesting as the personas themselves.

The thread skips the neuron-sweep details and turns into a debate over whether the result says anything about "thinking" or consciousness in LLMs. Almost nobody discusses the methodology; one opening comment raises hardware reliability.

**The hardware aside.** senileape connects the numerical-noise finding to cosmic-ray bit flips and asks whether AI accelerators used for decision-making will need ECC. Nobody picked this up.

**The main argument: does fragility show LLMs don't think?** proc0 opens by saying this kind of research should settle the "do LLMs think" question, calling the models pattern matchers at scale. The replies push back from several directions:
- **Brain damage analogy.** viraptor points out that local brain injuries can change personality dramatically. LLMs, trained for minimal redundancy, would show a more extreme version of the same effect. fzeindl counters that this takes damage to thousands of neurons, not one. kuhsaft and busssard answer on scale. Brains have tens of billions of neurons against hundreds of thousands in the model, so by percentage one Qwen neuron carries far more weight.
- **Emergence.** thoughtpeddler argues that surface personality is an emergent property, so flipping behavior via one unit doesn't show absence of thought. Human connectomics might show similar effects from tiny clusters. 0-_-0 asks why the same couldn't be done to a human. proc0 grants an analog but doubts a single neuron could yield a completely different yet coherent response.
- **Identical mechanism?** proc0 says we only know thinking from biology, so a match should be near-identical, or absent a predictive theory it is probably something else. adjejmxbdjdn and mellab2 reply that thinking can have many implementations, and that planes fly without flapping.
- **Fake versus real behavior.** proc0 argues there are more ways to fake conscious-looking behavior than to land on a different real one (Chinese room, philosophical zombie). kuhsaft asks why identical behavior should count as fake, and argues thinking and consciousness are behaviors, not processes. GoToRO and cyanydeez suggest that consciousness may itself be pattern matching, and that many people behave much as LLMs do.

The crux is unresolved: proc0 wants a theory of consciousness or a biologically matched result before granting that LLMs think, while the other side treats thinking as defined by behavior and substrate-independent.
